## 1. 확정된 아키텍처 결정

| 주제            | 결정 사항                                                    |
| --------------- | ------------------------------------------------------------ |
| 서비스명        | **Passport**                                                 |
| 서비스 성격     | 중앙 Identity / Authentication / Account / Global Tenant Management |
| 인증 방식       | External OIDC + Local Authentication                         |
| 인증 추상화     | 추상 `Authentication` 클래스를 공통 계약으로 정의하고 Local·OIDC 구현이 이를 상속. 향후 SAML 구현도 같은 계약으로 추가하며, 인증 결과는 공통 내부 인증 정보로 제공. SAML 자체 구현은 향후 범위. |
| OIDC 로그인 진입 | 테넌트 전용 로그인 링크와 공통 로그인 화면의 테넌트 코드 입력을 모두 지원. 식별한 대상 테넌트의 OIDC 설정만 사용하며 구체적인 URL·코드 형식과 UI는 후속 설계. |
| OIDC 설정 권한 | 테넌트 관리자는 자신의 테넌트 OIDC 설정을 플랫폼 관리자 승인 없이 등록·조회·변경·활성화·비활성화할 수 있음. 플랫폼 관리자는 전체 테넌트 설정을 관리할 수 있으며, 테넌트 관리자의 다른 테넌트 설정 조회·변경은 거부. |
| OIDC 설정 변경 | 발급자·클라이언트 ID 변경 또는 비활성화 등 인증 신뢰에 영향을 주는 변경은 해당 설정에 근거한 해당 테넌트의 기존 OIDC 인증 근거를 즉시 무효화하고 재인증 요구. 비활성화된 설정으로 재로그인 불가. 표시명·설명 변경은 기존 로그인 유지. 독립적인 Local 인증 및 다른 테넌트의 인증 근거에는 이 변경만으로 영향 없음. 상세 변경 분류·설정 버전·캐시·동시성 처리는 후속 설계. |
| 초기 OIDC Provider | Keycloak과 Auth0를 초기 연동·검증 대상으로 지정. 테넌트당 한 번에 하나의 OIDC Provider만 활성화. 구체적인 제품 버전·지원 설정과 API별 JWT Access Token·SSO 계약은 후속 설계. |
| 외부 Access Token 형식 | 초기 제품은 외부 JWT Access Token만 지원하며 opaque Access Token 및 이를 위한 검증 API 연동은 초기 지원 범위에서 제외. |
| 외부 OIDC 토큰  | 외부 Provider가 발급한 토큰을 Passport 자체 토큰으로 교환·재발급하지 않고 사용. |
| 외부 OIDC SSO   | 같은 테넌트 내 Passport 관리 포털과 Papyrus 등 연동 SaaS 간 이동 시 아이디·비밀번호 재입력 없는 SSO를 필수로 제공. 정책상 필요한 MFA·재인증은 별도 적용. API별 외부 Access Token 확보 및 로그인 상태·인증 컨텍스트 연계 방식은 후속 설계. |
| 자체 인증 토큰  | Local Authentication을 통해 Passport가 RFC 9068을 따르는 JWT Access Token을 발급할 수 있음. Local Access Token의 유효기간은 발급 후 30분이며, 로그인 유지 조건과 즉시 철회 정책은 별도로 적용. 별도의 신원 정보 전달용 JWT 또는 OIDC ID Token은 발급하지 않으며, 사용자 정보는 인증된 API로 조회. |
| Local 서명키 교체 | Local Access Token 서명키는 90일마다 자동 교체. 키 배포·전환 및 긴급 대응의 세부 계약은 후속 설계. |
| Local 토큰 수용 | Passport API와 Papyrus 등 연동 SaaS API 모두 Passport 발급 Local Access Token을 인증 수단으로 수용. 각 API의 audience 등 토큰 검증과 현재 접근 자격 검증은 필수이며, 구체적인 audience 구성·발급 방식·철회 검증 계약은 후속 설계. |
| 웹 포털 토큰   | Access Token은 브라우저 메모리에 저장하고 API에 Bearer 헤더로 전달. Refresh Token은 HttpOnly 쿠키에 저장하며 Secure·SameSite 및 CSRF 방어 적용. 페이지 새로고침 시 로그인 유지 조건을 충족하는 유효한 Refresh Token으로 Access Token을 다시 확보. 쿠키 속성·CSRF/XSS 방어·외부 OIDC 갱신 계약의 상세는 후속 설계. |
| JWT 검증 공통화 | Local Access Token과 외부 JWT Access Token은 발급자·테넌트별 검증 설정과 클레임 매핑을 적용하는 동일한 검증 엔진에서 처리. |
| 내부 인증 정보  | 검증 결과는 원본 발급자·Passport 사용자 신원·인증 방식·테넌트 인증 범위를 보존하는 공통 내부 인증 정보로 변환하여 사용. 외부 토큰의 재발급·교환은 수행하지 않음. |
| 프로토콜상 역할 | Passport를 **OIDC Provider** 또는 **OAuth2 Authorization Server**로 정의하지 않음. |
| MFA 개발 단계 | OTP 기반 MFA를 최초 제품(P0)에 포함. 첫 출시부터 OTP 등록·인증·해제·분실 복구, 테넌트별 설정 및 관련 관리 포털 UI를 제공. OTP 방식은 RFC 6238의 TOTP(시간 기반 OTP). 새 테넌트의 MFA는 기본 비활성화이며, 권한 있는 관리자가 명시적으로 활성화하면 해당 테넌트 접근 시 MFA 요구. 테넌트 관리자는 자신의 테넌트 MFA 설정을, 플랫폼 관리자는 전체 테넌트의 MFA 설정을 변경할 수 있음. 외부 OIDC MFA가 대상 테넌트 정책을 충족했음을 검증할 수 있으면 Passport 추가 OTP를 생략하고, 확인할 수 없으면 Passport TOTP 요구. Passport TOTP는 사용자·테넌트 조합 단위로 등록·관리하며, 같은 사용자도 테넌트마다 독립적인 TOTP를 각각 등록. 등록 정보와 비밀값을 테넌트별로 격리하고 MFA 정책 충족 여부는 대상 테넌트별 검증. MFA 완료 상태는 해당 테넌트의 현재 로그인이 유효한 동안 재사용하며 새 로그인 시 다시 검증. 웹 최대 8시간·기타 사용자 클라이언트 최대 7일 및 미사용 만료 조건을 따름. 분실 복구는 사용자·테넌트별 일회용 복구 코드와 관리자 본인 확인 후 초기화를 모두 제공. 복구 코드는 기존 계정 인증과 함께 사용하여 해당 테넌트의 TOTP를 재등록. 본인 확인 후 복구 초기화는 테넌트 관리자가 자신의 테넌트의 다른 구성원에 대해, 플랫폼 관리자가 전체 테넌트의 다른 사용자에 대해 수행할 수 있음. MFA 활성화 시 이미 유효한 로그인은 기존 유효기간까지 MFA 추가 요구를 유예하고 새 로그인부터 적용하며, 토큰 갱신으로 기존 로그인 유지 한도를 연장하지 않음. 다른 인증·인가 검사와 만료 조건은 계속 적용. 등록·해제·복구 및 기타 설정 변경 상세 절차와 Provider별 근거·정책 매핑 및 SaaS 전달·검증 계약은 후속 설계. |
| 개인정보        | Passport가 공통 가입자의 개인정보를 저장·관리. 필수 프로필 항목은 이메일과 표시 이름이며 실명·전화번호는 필수로 요구하지 않음. 표시 이름은 실명일 필요가 없음. 선택 프로필 항목은 프로필 사진·전화번호·실명. 테넌트 관리자는 자신의 테넌트 구성원이 입력한 실명·전화번호를 조회할 수 있음. |
| 초기 지원 지역 | 대한민국과 해외 고객을 처음부터 함께 대상으로 설계. 초기 지원 국가·지역은 대한민국, 미국, 일본, 대만, 캄보디아, 베트남, 태국, 러시아, 말레이시아, 인도네시아, 필리핀, 캐나다, 싱가포르. 초기에는 일반 기업의 공통 요구사항을 우선하고 특정 업종의 추가 요건은 후속 범위로 둠. 개인정보 수집 목적·그 외 행위자의 필드별 열람 범위 및 법령 검토를 반영한 최종 삭제·보존 정책은 별도 결정. |
| 초기 운영 규모 | 단일 Passport 설치에서 전체 테넌트 합계 등록 사용자 1,000,000명을 지원하는 것을 설계·검증 목표로 함. 관리 포털과 연동 SaaS를 합친 피크 동시 활성 사용자 수는 1,000명. 초기 API 처리량 목표는 접근 자격 검증 요청을 포함해 초당 100건(100 RPS). 목표 부하에서 조회·접근 자격 검증 API의 서버 응답 시간은 p95 100ms 이내(요청 수신부터 응답까지). 비밀번호 검증을 포함한 Local 로그인 API는 목표 부하에서 p95 500ms 이내(서버 요청 수신부터 응답까지). 단일 설치의 월간 시간 기준 가용성 목표(SLO)는 99.9%. 사전 공지·합의된 조건을 충족하는 계획 점검은 가용성 계산에서 제외하고 그 외 중단은 포함. 요청 구성·부하 지속 시간·테스트 환경, 그 외 API 지연 목표, 점검 공지·합의 절차·제외 시간 한도 및 측정 기준은 후속 설계. 장애 발생부터 정상 서비스 복구까지 RTO는 30분 이내. RPO는 15분으로 장애 직전 최대 15분간의 데이터 변경 손실을 허용하며, 복구 시나리오와 접근 차단·토큰 철회 등 보안 상태의 복구 처리는 후속 설계. |
| 계정 생명주기   | 가입, 비밀번호 변경, 계정 변경 및 탈퇴 등을 Passport가 담당. 본인 확인 후 탈퇴 확정 시 유예기간 없이 즉시 탈퇴를 완료하며 탈퇴 취소·기존 계정 복구는 제공하지 않음. 탈퇴 후 고객 문의 처리·분쟁 대응·보안 사고 조사·부정 이용 조사를 위해 일정 기간 프로필을 추가 보관. 추가 보관 대상은 기존에 수집한 이메일·표시 이름·전화번호·실명으로 한정하고 프로필 사진은 제외. 제품의 목표 추가 보관 기간은 탈퇴 시점부터 24시간. 최종 삭제·보존 정책은 국가별 법령 검토를 반영하여 확정하며 감사로그·백업 처리는 별도 검토. |
| OIDC 최초 가입 | 기존 Passport 계정이 없는 사용자가 대상 테넌트의 OIDC 인증에 성공하면 사용자 계정과 (issuer, subject) 기반 외부 신원 연결을 자동 생성. 별도의 Local 회원가입은 요구하지 않으며, 동일 이메일만으로 기존 계정에 자동 연결하지 않음. 테넌트 소속 부여는 테넌트 관리자가 일반 구성원 자동 등록 또는 관리자 사전 등록·초대 중 선택. 새 테넌트의 기본값은 관리자 사전 등록·초대이며, 자동 등록은 테넌트 관리자가 명시적으로 활성화. 관리자가 해지·비활성화한 멤버십은 OIDC 재로그인으로 자동 복구하지 않으며, 서비스 내 재가입 신청과 해당 테넌트 관리자 승인 후 복구. 승인 대기 중 접근 거부. 재가입 신청·승인 기능과 UI는 P1에 포함하며, OIDC 재로그인에 의한 자동 복구 금지와 기존 접근 차단은 P0에서도 적용. |
| 외부 신원 연결 | 최초 제품(P0)에 연결 기능·모델·UI를 포함. 기존 Passport 계정 재인증과 연결할 외부 OIDC 인증을 모두 완료한 뒤 사용자가 명시적으로 확인하면 직접 연결. 플랫폼 관리자 승인은 요구하지 않으며, 동일 이메일만으로 자동 연결하지 않음. 최초 OIDC 인증 시 동일 이메일의 기존 계정이 있으면 새 계정을 생성하지 않고 기존 계정 재인증 후 명시적 연결을 안내. 연결하려는 외부 신원이 이미 다른 사용자에게 연결되어 있으면 새 연결 요청을 거부하고 기존 연결을 유지. 계정 병합 및 외부 신원의 계정 간 이전은 이번 범위에서 제공하지 않음. |
| Local 가입 정책 | 관리자 초대·승인 없이 누구나 직접 계정을 만들 수 있는 공개 가입. 테넌트 소속과 SaaS 이용 권한은 별도로 부여. Local 계정의 정상 이용 전 이메일 소유 확인 필수. 확인 전에는 이메일 인증·재발송 등 가입 완료에 필요한 기능만 허용. |
| 테넌트 모델     | **Global Tenant 단일 모델**. 테넌트는 논리적인 고객 조직이며 법인·회사와 일대일 대응을 강제하지 않음. 같은 회사도 운영 목적에 따라 여러 독립 테넌트를 가질 수 있음. |
| 테넌트 소유권   | Passport가 전역 테넌트의 생성·관리 및 식별자 소유.            |
| 테넌트 생성 권한 | 이메일 소유 확인을 완료한 사용자가 플랫폼 관리자 승인 없이 Passport를 통해 새 테넌트를 직접 생성할 수 있음. 생성자를 해당 테넌트의 첫 관리자로 자동 등록하여 구성원·설정 등을 관리할 수 있도록 하며, 플랫폼 관리자 권한은 부여하지 않음. |
| 테넌트 식별자   | 모든 연동 SaaS가 공통 `tenant_id` 사용.                       |
| 서비스별 테넌트 | **도입하지 않음** (`ApplicationTenant` 및 Hybrid Tenant 구조 제외) |
| SaaS 책임       | 각 SaaS는 자신의 도메인 데이터, 워크스페이스·공간 및 세부 리소스 접근 정책을 관리. |
| 사용자 접근     | 전역 테넌트 소속과 SaaS 이용 자격, SaaS 내부 리소스 권한을 구분. |
| SaaS 이용 자격 | TenantApplication으로 테넌트 단위로만 관리. 공통 인증·계정·테넌트·멤버십·MFA 검증을 충족하는 모든 활성 구성원이 해당 테넌트에서 활성화된 서비스를 이용할 수 있음. 사용자별 별도 서비스 허가 및 ApplicationMembership은 도입하지 않으며 리소스별 권한은 각 SaaS가 관리. |
