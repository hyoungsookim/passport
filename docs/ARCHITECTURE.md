## 1. 확정된 아키텍처 결정

| 주제            | 결정 사항                                                    |
| --------------- | ------------------------------------------------------------ |
| 서비스명        | **Passport**                                                 |
| 서비스 성격     | 중앙 Identity / Authentication / SSO / Account / Global Tenant Management |
| 인증 방식       | External OIDC + Local Authentication                         |
| 인증 추상화     | 추상 `Authentication` 클래스를 공통 계약으로 정의하고 Local·OIDC 구현이 이를 상속. 향후 SAML 구현도 같은 계약으로 추가하며, 인증 결과는 공통 내부 인증 정보로 제공. SAML 자체 구현은 향후 범위. |
| OIDC 로그인 진입 | 테넌트 전용 로그인 링크와 공통 로그인 화면의 테넌트 코드 입력을 모두 지원. 식별한 대상 테넌트의 OIDC 설정만 사용하며 구체적인 URL·코드 형식과 UI는 후속 설계. |
| OIDC 설정 권한 | 테넌트 관리자는 자신의 테넌트 OIDC 설정을 플랫폼 관리자 승인 없이 등록·조회·변경·활성화·비활성화할 수 있음. 플랫폼 관리자는 전체 테넌트 설정을 관리할 수 있으며, 테넌트 관리자의 다른 테넌트 설정 조회·변경은 거부. |
| OIDC 설정 변경 | 발급자·클라이언트 ID 변경 또는 비활성화 등 인증 신뢰에 영향을 주는 변경은 해당 설정에 근거한 해당 테넌트의 기존 OIDC 인증 근거를 즉시 무효화하고 재인증 요구. 비활성화된 설정으로 재로그인 불가. 표시명·설명 변경은 기존 로그인 유지. 독립적인 Local 인증 및 다른 테넌트의 인증 근거에는 이 변경만으로 영향 없음. 상세 변경 분류·설정 버전·캐시·동시성 처리는 후속 설계. |
| 초기 OIDC Provider | Keycloak과 Auth0를 초기 연동·검증 대상으로 지정. 테넌트당 한 번에 하나의 OIDC Provider만 활성화. 구체적인 제품 버전·지원 설정과 OIDC 인증·로그인 상태 연계 계약은 후속 설계. |
| 외부 Access Token 형식 | OIDC 연동 과정에서 외부 Access Token을 검증할 경우 초기 제품은 JWT만 지원하며 opaque 토큰 검증 API 연동은 제외. 외부 토큰은 Passport API와 연동 SaaS API의 인증 수단으로 직접 수용하지 않음. |
| 외부 OIDC 토큰  | Passport가 대상 테넌트의 외부 OIDC 인증 결과를 검증하고 사용자 연결·계정·테넌트·멤버십·MFA·이용 자격을 확인한 뒤 Passport 자체 JWT Access Token을 발급. 외부 인증 출처와 테넌트 범위를 보존. |
| 외부 OIDC SSO   | 같은 테넌트 내 Passport 관리 포털과 Papyrus 등 연동 SaaS 간 이동 시 아이디·비밀번호 재입력 없는 SSO를 필수로 제공. API는 Passport 발급 Access Token을 사용하며 정책상 필요한 MFA·재인증은 별도 적용. API별 토큰 발급과 로그인 상태·인증 컨텍스트 연계 방식은 후속 설계. |
| 자체 인증 토큰  | Local·외부 OIDC 인증 모두 Passport가 RFC 9068을 따르는 JWT Access Token을 발급. Local·OIDC 인증 후 발급하는 Passport Access Token의 유효기간은 모두 발급 후 30분. 로그인 유지 조건과 즉시 철회 정책은 두 방식에 공통 적용. 별도의 신원 정보 전달용 JWT 또는 OIDC ID Token은 발급하지 않으며 사용자 정보는 인증된 API로 조회. |
| 자체 토큰 서명키 교체 | Local·OIDC 인증 후 발급하는 Passport Access Token 서명키는 모두 90일마다 자동 교체. 키 배포·전환 및 긴급 대응의 세부 계약은 후속 설계. |
| 자체 토큰 수용  | Passport API와 Papyrus 등 연동 SaaS API는 Local·OIDC 인증 후 Passport가 발급한 Access Token을 인증 수단으로 수용. 각 API의 audience·토큰 검증과 현재 접근 자격 검증은 필수이며, 구체적인 audience 구성·발급 방식·철회 검증 계약은 후속 설계. |
| 웹 인증·토큰 관리 | Passport 관리 포털과 연동 SaaS 웹은 BFF 방식을 사용. 브라우저는 서비스별 HttpOnly·Secure 로그인 쿠키의 불투명 세션 식별자로 자신의 BFF를 호출하고, Passport Access/Refresh Token은 BFF 서버에서 보호하여 보관·갱신. BFF는 사용자 Access Token으로 리소스 API를 호출하며 토큰을 브라우저 메모리·웹 저장소·쿠키·응답 본문에 전달하지 않음. SameSite·CSRF 방어 적용. 모바일 등 직접 API 클라이언트는 기존 토큰 방식을 유지. 쿠키·서버 간 로그인 연계의 상세 계약은 API 설계에서 정의. |
| BFF 세션·책임 | BFF의 쿠키 인증과 리소스 API의 Bearer 인증을 분리. 세션 유효기간·활동·테넌트·MFA·철회는 연결된 Passport 로그인 정책을 따르며 세션만으로 접근 검증을 우회하지 않음. 로그아웃·강제 종료·복원 등 기존 정책의 종료 범위에 연결된 BFF 세션도 무효화. 각 SaaS는 자신의 웹 BFF를 담당하며 Passport BFF는 기존 FastAPI 프로세스 안에 구성 가능. 서비스 간 쿠키·Refresh Token 공유에 의존하지 않고 Passport 로그인 연계로 SSO 제공. |
| JWT 검증 공통화 | Passport 발급 Access Token과 OIDC 연동 시 검증하는 외부 JWT Access Token은 공통 검증 엔진을 사용하되 발급자·테넌트·토큰 용도별 검증 설정과 클레임 매핑을 분리. API는 Passport 발급 토큰만 수용하며 외부 JWT 검증은 OIDC 연동 경계에서 수행. |
| 내부 인증 정보  | 검증 결과는 Passport 사용자 신원·인증 방식·테넌트 인증 범위를 보존하는 공통 내부 인증 정보로 변환. OIDC 인증은 외부 issuer·subject와 대상 OIDC 설정·MFA 근거를 보존하며 자체 토큰의 발급자는 Passport로 구분. 상세 클레임·서버 상태 연계 계약은 후속 설계. |
| 프로토콜상 역할 | Passport는 Local·외부 OIDC 인증 후 자체 Access Token을 발급하는 주체. 초기 범위에 완전한 OIDC Provider·OAuth2 Authorization Server의 표준 기능 전체나 범용 RFC 8693 토큰 교환 엔드포인트는 포함하지 않음. |
| OIDC 인증 생명주기 | OIDC 로그인에도 Passport Refresh Token·로그인 유지 한도·즉시 철회 정책을 적용. OIDC 신뢰 설정 변경 시 관련 Passport 로그인과 Access/Refresh Token도 즉시 무효화. 자체 Access Token은 Local과 동일하게 30분 유효·서명키 90일 자동 교체를 적용. 외부 계정 차단·비활성화를 신뢰할 수 있는 방식으로 확인하면, 해당 외부 신원에 근거한 해당 테넌트의 Passport 로그인 전체와 연결된 Access/Refresh Token을 즉시 무효화하고 후속 API 접근·갱신·신규 로그인을 거부. 독립적인 Local 로그인과 다른 테넌트 로그인은 이 조치만으로 종료하지 않음. Provider 연동이 정상일 때 사용 중인 OIDC 로그인의 외부 계정 차단·비활성화를 상태 변경 시점부터 최대 5분 이내 감지하는 것을 설계·검증 목표로 함. 감지 수단·Provider별 지원 가능성과 키 배포·전환 상세는 후속 설계하며 외부 상태 변경의 자동 전파를 가정하지 않음. |
| Passport 로그아웃 | 현재 로그인 및 모든 기기 로그아웃은 선택한 범위의 Passport 로그인과 Access/Refresh Token을 종료·무효화. 외부 Provider 로그아웃은 요청하지 않고 외부 로그인은 유지하며, 이후 OIDC 로그인 시 외부 로그인 상태에 따라 자격 증명 재입력 없이 인증될 수 있음. |
| 외부 Provider 로그아웃 | Provider 로그아웃의 사실과 대상을 신뢰할 수 있는 방식으로 확인하면, 해당 테넌트에서 로그아웃 대상 외부 로그인에 연결된 Passport 로그인과 Access/Refresh Token을 즉시 무효화하고 후속 API 접근·갱신을 거부. 독립적인 Local 로그인과 다른 테넌트 로그인은 이 조치만으로 종료하지 않음. Provider별 로그아웃 통지 지원 여부·검증·대상 매핑·전달 지연은 후속 연동 설계에서 검증. |
| 외부 토큰 명시적 철회 | 외부 Provider가 보안 조치로 토큰을 명시적으로 철회한 사실과 대상을 신뢰할 수 있게 확인하면, 해당 테넌트에서 철회 대상 인증에 연결된 Passport 로그인과 Access/Refresh Token을 즉시 무효화하고 후속 API 접근·갱신을 거부. 독립적인 Local·다른 테넌트 로그인은 이 조치만으로 종료하지 않음. 정상적인 외부 토큰 만료·교체는 이 조항의 명시적 철회로 취급하지 않음. Provider별 감지·검증·대상 매핑·전달 지연은 후속 연동 설계에서 검증. |
| OIDC 연동 장애 | 통신 장애 등으로 외부 계정 상태를 확인할 수 없는 동안 기존 Passport Access Token은 남은 유효기간까지 API 접근에 사용할 수 있음(최대 30분). 신규 OIDC 로그인과 OIDC 기반 토큰 갱신은 상태 확인이 복구될 때까지 거부. 토큰 만료·철회 및 계정·테넌트·멤버십·MFA·서비스 이용 자격 검증은 계속 적용하며, 이미 확인한 차단·비활성화를 장애를 이유로 해제하지 않음. 독립적인 Local 로그인은 기존 정책을 따름. |
| MFA 개발 단계 | OTP 기반 MFA를 최초 제품(P0)에 포함. 첫 출시부터 OTP 등록·인증·해제·분실 복구, 테넌트별 설정 및 관련 관리 포털 UI를 제공. OTP 방식은 RFC 6238의 TOTP(시간 기반 OTP). 새 테넌트의 MFA는 기본 비활성화이며, 권한 있는 관리자가 명시적으로 활성화하면 해당 테넌트 접근 시 MFA 요구. 테넌트 관리자는 자신의 테넌트 MFA 설정을, 플랫폼 관리자는 전체 테넌트의 MFA 설정을 변경할 수 있음. 외부 OIDC MFA가 대상 테넌트 정책을 충족했음을 검증할 수 있으면 Passport 추가 OTP를 생략하고, 확인할 수 없으면 Passport TOTP 요구. Passport TOTP는 사용자·테넌트 조합 단위로 등록·관리하며, 같은 사용자도 테넌트마다 독립적인 TOTP를 각각 등록. 등록 정보와 비밀값을 테넌트별로 격리하고 MFA 정책 충족 여부는 대상 테넌트별 검증. MFA 완료 상태는 해당 테넌트의 현재 로그인이 유효한 동안 재사용하며 새 로그인 시 다시 검증. 웹 최대 8시간·기타 사용자 클라이언트 최대 7일 및 미사용 만료 조건을 따름. 분실 복구는 사용자·테넌트별 일회용 복구 코드와 관리자 본인 확인 후 초기화를 모두 제공. 복구 코드는 기존 계정 인증과 함께 사용하여 해당 테넌트의 TOTP를 재등록. 본인 확인 후 복구 초기화는 테넌트 관리자가 자신의 테넌트의 다른 구성원에 대해, 플랫폼 관리자가 전체 테넌트의 다른 사용자에 대해 수행할 수 있음. MFA 활성화 시 이미 유효한 로그인은 기존 유효기간까지 MFA 추가 요구를 유예하고 새 로그인부터 적용하며, 토큰 갱신으로 기존 로그인 유지 한도를 연장하지 않음. 다른 인증·인가 검사와 만료 조건은 계속 적용. 등록 및 기타 설정 변경 상세 절차, 개인 OTP 해제·관리자 복구의 API·UI 세부 계약과 Provider별 근거·정책 매핑 및 SaaS 전달·검증 계약은 후속 설계. |
| 개인 OTP 해제 | 사용자가 자신의 Passport TOTP 등록을 해제할 때 계정 재인증과 해당 사용자·테넌트의 현재 OTP 검증을 모두 요구. Local 로그인은 비밀번호 재확인, OIDC 로그인은 해당 테넌트 Provider 재인증을 적용하며 기존 로그인 상태만으로 대체하지 않음. OTP 분실 시에는 기존 복구 코드·관리자 복구 절차를 사용. 개인 OTP 해제로 테넌트의 MFA 활성화 설정은 변경하지 않음. |
| 관리자 OTP 복구 | OTP·복구 코드를 분실하여 관리자 초기화를 요청할 때 사용자 계정 재인증과 관리자의 별도 본인 확인을 모두 요구. Local은 비밀번호, OIDC는 대상 테넌트 Provider 재인증을 적용. 관리자는 사전에 확인된 조직 연락 경로·대면 등을 통해 추가 확인하고 기존 복구 권한 범위 내에서 해당 사용자·테넌트의 TOTP를 초기화하여 재등록하도록 함. 처리자·대상·사유를 감사 기록에 남김. |
| 개인정보        | Passport가 공통 가입자의 개인정보를 저장·관리. 필수 프로필 항목은 이메일과 표시 이름이며 실명·전화번호는 필수로 요구하지 않음. 표시 이름은 실명일 필요가 없음. 선택 프로필 항목은 프로필 사진·전화번호·실명. 테넌트 관리자는 자신의 테넌트에서 정상 이용 중인 구성원이 입력한 실명·전화번호를 조회할 수 있음. |
| 프로필 수집·이용 목적 | 이메일은 계정 식별·이메일 소유 확인·계정 복구·보안 알림, 표시 이름과 프로필 사진은 화면·프로필 표시 및 서비스 내 사용자 식별, 실명은 테넌트 관리자의 조직 구성원 식별, 전화번호는 테넌트 관리자의 구성원 업무 연락에 사용. 기존 필수·선택 항목 구분은 유지하며 국가별 법령을 반영한 최종 개인정보 처리 명세는 별도 검토. |
| 정상 계정 프로필 열람 | 본인은 자신의 모든 프로필 항목, 테넌트 관리자는 자신의 테넌트 구성원의 모든 프로필 항목, 일반 구성원은 같은 테넌트의 다른 구성원의 표시 이름·프로필 사진을 열람. 플랫폼 관리자 역할은 이메일·표시 이름·프로필 사진을 열람. 연동 SaaS에는 이용 자격이 있는 테넌트·사용자 범위에서 사용자·테넌트 식별자와 이메일·표시 이름·프로필 사진을 제공. 실명·전화번호는 본인과 해당 테넌트 관리자만 열람하며 플랫폼 관리자 역할이나 SaaS 연동 권한만으로는 조회 불가. 탈퇴 후 추가 보관 정보는 별도 정책 적용. |
| 탈퇴 후 보관 정보 열람 | 허용된 추가 보관 기간 내에 플랫폼 관리자와 탈퇴 시점 소속 테넌트의 현재 권한 있는 관리자에게 이메일·표시 이름·전화번호·실명 열람을 허용. 고객 문의·분쟁 대응·보안 사고·부정 이용 조사 목적으로 제한하며 테넌트 관리자는 자신의 테넌트 관련 목적으로만 조회. 조회자·대상·사유를 감사 기록에 남기고 일반 구성원·연동 SaaS에는 제공하지 않음. |
| 감사로그 보존기간 | 운영 저장소의 로그인·설정 변경·관리자 조회 등 감사로그의 제품 기본 보존기간은 기록 시점부터 365일이며 백업 사본의 보존기간과 구분. 탈퇴 후 프로필 추가 보관 목표 24시간과 구분. 최종 보존·삭제 기준과 예외는 국가별 법령·고객 계약 검토를 반영하여 확정. |
| DB 백업 보존기간 | DB 백업의 제품 기본 보존기간은 백업 생성 시점부터 30일. 운영 DB에서 삭제한 개인정보가 과거 백업에는 폐기 시점까지 남을 수 있으며 감사로그 등 백업 사본도 이 보존 기준을 적용. 백업은 장애 복구 용도로 제한하고 복원 시 탈퇴·삭제 상태를 재적용하여 계정·삭제 정보의 재노출을 방지. 최종 보존·삭제 기준과 예외는 법령·고객 계약 검토를 반영하며 백업·복원·삭제 재적용 절차는 후속 설계·검증. |
| 초기 지원 지역 | 대한민국과 해외 고객을 처음부터 함께 대상으로 설계. 초기 지원 국가·지역은 대한민국, 미국, 일본, 대만, 캄보디아, 베트남, 태국, 러시아, 말레이시아, 인도네시아, 필리핀, 캐나다, 싱가포르. 초기에는 일반 기업의 공통 요구사항을 우선하고 특정 업종의 추가 요건은 후속 범위로 둠. 프로필 수집·이용 목적은 위 결정에 따르며, 탈퇴 후 추가 보관 정보의 열람 범위는 위 결정에 따르며 법령 검토를 반영한 최종 삭제·보존 정책은 별도 결정. |
| 백업 복원 후 인증 | 백업 복원 후 해당 Passport 설치의 기존 Local·OIDC 로그인을 모두 종료하고 복구 전 발급된 Passport Access/Refresh Token을 무효화하여 재로그인을 요구. 탈퇴·계정 차단·멤버십 해지·개인정보 삭제 상태는 별도로 검증·재적용하며 로그인 종료만으로 대체하지 않음. 서비스 재개 전 기존 토큰 거부와 보안 상태 검증·재적용을 보장하는 복구 절차는 후속 설계·검증. |
| 계획 점검 사전 공지 | 가용성 계산에서 제외하려는 계획 점검은 점검 시작 최소 72시간 전에 예정 시간과 영향 범위를 공지하고 기존 합의 조건도 충족해야 함. 공지 기한 미준수 등 제외 조건을 충족하지 않는 중단은 가용성 계산에 포함. 구체적인 공지 전달·합의 절차와 월간 제외 시간 한도는 후속 결정·설계. |
| 초기 운영 규모 | 단일 Passport 설치에서 전체 테넌트 합계 등록 사용자 1,000,000명을 지원하는 것을 설계·검증 목표로 함. 관리 포털과 연동 SaaS를 합친 피크 동시 활성 사용자 수는 1,000명. 초기 API 처리량 목표는 접근 자격 검증 요청을 포함해 초당 100건(100 RPS). 목표 부하에서 조회·접근 자격 검증 API의 서버 응답 시간은 p95 100ms 이내(요청 수신부터 응답까지). 비밀번호 검증을 포함한 Local 로그인 API는 목표 부하에서 p95 500ms 이내(서버 요청 수신부터 응답까지). 단일 설치의 월간 시간 기준 가용성 목표(SLO)는 99.9%. 사전 공지·합의된 조건을 충족하는 계획 점검은 가용성 계산에서 제외하고 그 외 중단은 포함. 요청 구성·부하 지속 시간·테스트 환경, 그 외 API 지연 목표, 점검의 최소 72시간 전 공지 기준은 위 결정에 따르며 공지 전달·합의 절차·월간 제외 시간 한도 및 측정 기준은 후속 결정·설계. 장애 발생부터 정상 서비스 복구까지 RTO는 30분 이내. RPO는 15분으로 장애 직전 최대 15분간의 데이터 변경 손실을 허용하며, 백업 복원 후 기존 로그인·토큰은 위 결정에 따라 모두 무효화. 구체적인 복구 시나리오와 탈퇴·접근 차단·토큰 철회·멤버십 해지·삭제 상태 검증·재적용 절차는 후속 설계. |
| 계정 생명주기   | 가입, 비밀번호 변경, 계정 변경 및 탈퇴 등을 Passport가 담당. 본인 확인 후 탈퇴 확정 시 유예기간 없이 즉시 탈퇴를 완료하며 탈퇴 취소·기존 계정 복구는 제공하지 않음. 탈퇴 후 고객 문의 처리·분쟁 대응·보안 사고 조사·부정 이용 조사를 위해 일정 기간 프로필을 추가 보관. 추가 보관 대상은 기존에 수집한 이메일·표시 이름·전화번호·실명으로 한정하고 프로필 사진은 제외. 제품의 목표 추가 보관 기간은 탈퇴 시점부터 24시간. 최종 삭제·보존 정책은 국가별 법령 검토를 반영하여 확정. 감사로그는 기록 시점부터 365일을 제품 기본 보존기간으로 하며, DB 백업은 생성 시점부터 30일을 제품 기본 보존기간으로 하며 법령·고객 계약에 따른 예외와 세부 삭제·복원 절차는 별도 검토. |
| OIDC 최초 가입 | 기존 Passport 계정이 없는 사용자가 대상 테넌트의 OIDC 인증에 성공하면 사용자 계정과 (issuer, subject) 기반 외부 신원 연결을 자동 생성. 별도의 Local 회원가입은 요구하지 않으며, 동일 이메일만으로 기존 계정에 자동 연결하지 않음. 테넌트 소속 부여는 테넌트 관리자가 일반 구성원 자동 등록 또는 관리자 사전 등록·초대 중 선택. 새 테넌트의 기본값은 관리자 사전 등록·초대이며, 자동 등록은 테넌트 관리자가 명시적으로 활성화. 관리자가 해지·비활성화한 멤버십은 OIDC 재로그인으로 자동 복구하지 않으며, 서비스 내 재가입 신청과 해당 테넌트 관리자 승인 후 복구. 승인 대기 중 접근 거부. 재가입 신청·승인 기능과 UI는 P1에 포함하며, OIDC 재로그인에 의한 자동 복구 금지와 기존 접근 차단은 P0에서도 적용. |
| 외부 신원 연결 | 최초 제품(P0)에 연결 기능·모델·UI를 포함. 기존 Passport 계정 재인증과 연결할 외부 OIDC 인증을 모두 완료한 뒤 사용자가 명시적으로 확인하면 직접 연결. 플랫폼 관리자 승인은 요구하지 않으며, 동일 이메일만으로 자동 연결하지 않음. 최초 OIDC 인증 시 동일 이메일의 기존 계정이 있으면 새 계정을 생성하지 않고 기존 계정 재인증 후 명시적 연결을 안내. 연결하려는 외부 신원이 이미 다른 사용자에게 연결되어 있으면 새 연결 요청을 거부하고 기존 연결을 유지. 계정 병합 및 외부 신원의 계정 간 이전은 이번 범위에서 제공하지 않음. |
| Local 가입 정책 | 관리자 초대·승인 없이 누구나 직접 계정을 만들 수 있는 공개 가입. 테넌트 소속과 SaaS 이용 권한은 별도로 부여. Local 계정의 정상 이용 전 이메일 소유 확인 필수. 확인 전에는 이메일 인증·재발송 등 가입 완료에 필요한 기능만 허용. |
| 테넌트 모델     | **Global Tenant 단일 모델**. 테넌트는 논리적인 고객 조직이며 법인·회사와 일대일 대응을 강제하지 않음. 같은 회사도 운영 목적에 따라 여러 독립 테넌트를 가질 수 있음. |
| 테넌트 소유권   | Passport가 전역 테넌트의 생성·관리 및 식별자 소유.            |
| 테넌트 생성 권한 | 이메일 소유 확인을 완료한 사용자가 플랫폼 관리자 승인 없이 Passport를 통해 새 테넌트를 직접 생성할 수 있음. 생성자를 해당 테넌트의 첫 관리자로 자동 등록하여 구성원·설정 등을 관리할 수 있도록 하며, 플랫폼 관리자 권한은 부여하지 않음. |
| 테넌트 식별자   | 모든 연동 SaaS가 공통 `tenant_id` 사용.                       |
| 서비스별 테넌트 | **도입하지 않음** (`ApplicationTenant` 및 Hybrid Tenant 구조 제외) |
| SaaS 책임       | 각 SaaS는 자신의 도메인 데이터, 워크스페이스·공간 및 세부 리소스 접근 정책을 관리. |
| 사용자 접근     | 전역 테넌트 소속과 SaaS 이용 자격, SaaS 내부 리소스 권한을 구분. |
| SaaS 이용 자격 | TenantApplication으로 테넌트 단위로만 관리. 공통 인증·계정·테넌트·멤버십·MFA 검증을 충족하는 모든 활성 구성원이 해당 테넌트에서 활성화된 서비스를 이용할 수 있음. 사용자별 별도 서비스 허가 및 ApplicationMembership은 도입하지 않으며 리소스별 권한은 각 SaaS가 관리. |
