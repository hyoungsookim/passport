# Passport 개발 요구사항 정의서 (SRS 초안)

- **문서 버전:** 0.1
- **작성일:** 2026-10-25
- **상태:** 초안 — 확정된 아키텍처 결정과 권장 구현 요구사항을 구분함
- **대상:** Passport Frontend, Backend, Papyrus 등 연동 SaaS
- **범위:** 기능, 데이터, 보안, SaaS 연동, 사용자 화면, 비기능, 검증 기준

## 1. 문서 목적과 요구사항 관리 기준

이 문서는 Passport 개발의 기준선(Baseline)을 정의한다. Passport는 여러 기업용 SaaS가 공통으로 활용하는 **Authentication, Identity, Account & Global Tenant Management Service**이다. 구현을 시작하기 전에 확정된 요구사항과 추가 결정이 필요한 정책을 구분하여 무분별한 범위 확장을 방지한다.

**결정 상태**

- **확정:** 기존 논의에서 사용자가 명시적으로 결정한 사항.
- **권장:** 현재까지의 결정에 부합하는 구현 제안이며 최종 승인 대상.
- **미결:** 제품 정책 또는 프로토콜 계약을 먼저 결정해야 하는 사항.

**우선순위**

- **P0:** 최소 서비스(MVP) 운영에 필수.
- **P1:** 초기 정식 운영 또는 기업 고객 확대 전에 필요.
- **P2:** 장기 확장 기능.

> 이 문서에서 `해야 한다`는 표현은 **해당 항목이 승인되었을 때의 구현·검증 기준**을 의미한다. `권장`과 `미결`을 사용자가 이미 확정한 것으로 간주하지 않는다.

### 2.1 이번 범위에서 제외할 것

- OAuth2 Authorization Server의 표준 인증/토큰 엔드포인트 전체 제공
- OIDC Provider 기능 및 Discovery를 제공한다는 대외적 약속
- 임의의 외부 토큰을 수용하는 범용 RFC 8693 토큰 교환 서버(OIDC 로그인 검증 후 자체 Access Token 발급은 포함)
- 외부 opaque Access Token 검증 API 연동(초기 제품 범위에서 제외)
- 서비스별 독립 테넌트 또는 Hybrid Tenant
- 사용자별 SaaS 이용 자격 및 `ApplicationMembership` 모델
- 서로 다른 Passport 계정의 병합 및 외부 신원의 계정 간 이전
- Papyrus 문서·위키 공간·페이지의 직접 관리
- 자체 구현한 범용 RBAC/ABAC 정책 엔진
- Microservices로 분리된 Passport Backend

> **토큰 용어:** Local·OIDC 인증 후 Passport는 JWT Access Token과 별개인 `Identity JWT` 또는 표준 OIDC `ID Token`을 발급하지 않는다. 사용자 정보는 유효한 Access Token으로 인증된 사용자 조회 API를 통해 제공한다. 외부 OIDC Provider가 발급한 ID Token의 수신·검증은 외부 OIDC 인증 요구사항을 따른다.

## 4. 기능 요구사항

### 4.1 Authentication: Local

Local 인증은 테넌트별 OIDC 설정과 별개로 기존과 동일하게 제공한다. Local 인증을 완료한 사용자는 소속 테넌트를 선택하여 접근할 수 있으며, 계정 상태·테넌트 상태·현재 멤버십·MFA·서비스 이용 자격 검증을 모두 충족해야 한다.

**Passport Access Token 수용 범위(확정):** Passport API와 Papyrus 등 연동 SaaS API는 Local·OIDC 인증 후 Passport가 발급한 JWT Access Token을 인증 수단으로 수용한다. 각 API는 자신의 audience 등 토큰 검증 계약과 현재 접근 자격을 검증해야 하며, 로그인 성공만으로 모든 SaaS의 이용 권한을 부여하지 않는다. 구체적인 audience 구성·발급 방식 및 SaaS의 철회 상태 검증 계약은 후속 설계한다.

| ID          | 요구사항                                                     | 우선순위 | 상태 |
| ----------- | ------------------------------------------------------------ | -------- | ---- |
| FR-AUTH-001 | Local 계정은 안전하게 보관된 자격 증명으로 로그인할 수 있어야 한다. | P0       | 확정 |
| FR-AUTH-002 | 인증 성공 시 Passport가 서명한 JWT Access Token을 발급할 수 있어야 한다. 토큰 포맷은 FR-AUTH-008-01의 공통 표준을 따른다. | P0       | 확정 |
| FR-AUTH-003 | 사용자는 본인의 비밀번호를 변경할 수 있어야 한다.            | P0       | 확정 |
| FR-AUTH-004 | 비밀번호 분실 시 검증된 복구 수단을 이용한 재설정 절차를 제공한다. | P1       | 확정 |
| FR-AUTH-005 | 탈퇴·차단·비활성 상태의 계정은 신규 로그인 및 허가되지 않은 작업이 거부되어야 한다. | P0       | 확정 |
| FR-AUTH-006 | 로그인 실패 횟수 제한, 속도 제한 및 계정 열거 방지 메시지를 적용한다. | P0       | 확정 |
| FR-AUTH-007 | 비밀번호는 평문·복호화 가능한 형태가 아닌 적응형 해시(예: Argon2id)로 저장한다. | P0       | 확정 |
| FR-AUTH-008 | Local·OIDC 인증 후 Passport가 발급하는 JWT Access Token의 유효기간은 모두 발급 후 30분으로 한다. 해당 Access Token 서명키는 모두 90일마다 자동 교체한다. 키 식별자, 검증 규칙 및 키 교체 세부 절차는 후속 설계한다. 로그인 유지 시간과 즉시 철회 정책은 Local·OIDC 로그인에 공통 적용한다. 외부 Provider 토큰의 수명은 Provider별 연동 계약에서 정한다. | P0       | 확정 |
| FR-AUTH-008-01 | Local·OIDC 인증 후 발급하는 Passport JWT Access Token은 RFC 9068의 JWT Access Token 프로파일을 따른다. `typ`은 `at+jwt`로 명시하고, `iss`, `sub`, `aud`, `exp`, `iat`, `jti`, `client_id` 등 필수 클레임과 서명·검증 규칙을 적용한다. 발급자 `iss`는 Passport, 사용자 `sub`는 Passport 사용자 식별자를 사용한다. | P0       | 확정 |
| FR-AUTH-008-02 | Passport 발급 Access Token과 OIDC 연동 시 검증하는 외부 JWT Access Token의 파싱·서명·표준 클레임 검증은 동일한 JWT 검증 엔진에서 처리하되, 발급자·테넌트·토큰 용도별 검증 설정과 클레임 매핑을 분리한다. Passport API와 연동 SaaS API는 Passport 발급 Access Token만 수용하며 외부 JWT 검증은 Passport의 OIDC 연동 경계에서 수행한다. | P0       | 확정 |
| FR-AUTH-008-03 | 공통 검증 엔진은 API 인증 시 Passport 발급자·알고리즘·검증 키·호출 API audience·토큰 용도·필수 클레임을 검증하고, 외부 JWT 검증 시 대상 테넌트의 OIDC 신뢰 설정과 해당 토큰의 용도·대상자를 적용한다. 검증되지 않은 토큰의 값만으로 신뢰할 발급자나 키를 추가하거나 다른 테넌트의 OIDC 신뢰 설정을 재사용하지 않는다. 외부 ID Token과 외부 Access Token은 API 인증 수단으로 허용하지 않는다. | P0       | 확정 |
| FR-AUTH-008-04 | 검증 결과는 Passport 사용자 신원·인증 방식·테넌트 인증 범위를 표현하는 공통 내부 인증 정보로 변환한다. 외부 신원은 `(issuer, subject)`로 Passport 사용자에 매핑하며 원본 외부 발급자·대상 OIDC 설정·검증된 MFA 근거를 보존한다. 이후 계정·테넌트·멤버십·MFA·이용 자격 검사는 공통 처리한다. **FR-AUTH-009 세분화:** 웹 관리 포털과 연동 SaaS 웹은 BFF로 전환한다. 브라우저는 로그인 세션 쿠키로 자신의 BFF를 호출하며, BFF는 서버에서 Passport Access/Refresh Token을 보관·갱신하고 Access Token으로 리소스 API를 호출한다. 모바일 등 직접 API 클라이언트는 기존 Access/Refresh Token 방식을 유지한다. 웹 최대 8시간·미사용 30분, 기타 사용자 클라이언트 최대 7일·미사용 3일 및 사용자 활동 기준을 유지한다. Local·OIDC 인증 후 Passport Access Token의 수명은 모두 30분이며 로그인 유지·철회 상태와 최신 접근 자격 검사는 별도로 계속 적용한다. 현재/전체 로그아웃·비밀번호 변경·계정 차단·Refresh Token 재사용 탐지 등의 기존 종료 범위에 연결된 BFF 세션도 무효화한다. OIDC 로그인에도 동일한 정책을 적용하고 외부 인증 출처와 테넌트 범위를 보존한다. 이 결정으로 모바일 앱 개발 범위를 추가하지 않는다. BFF 세션·쿠키·CSRF/XSS 방어, 외부 OIDC 상태와 갱신의 연계 및 SaaS의 철회 검증 상세는 후속 설계한다.

**웹 BFF 인증·토큰 저장·전달(확정):** Local·OIDC 로그인 모두 브라우저에는 서비스별 불투명 세션 식별자의 HttpOnly·Secure 로그인 쿠키를 설정하고 SameSite·CSRF 방어를 적용한다. Passport Access/Refresh Token은 BFF 서버에서 보호하여 보관하며 브라우저에 전달하지 않는다. BFF는 세션과 연결된 사용자 Access Token을 `Authorization: Bearer`로 리소스 API에 전달하고, 필요할 때 서버에서 Refresh Token을 회전·갱신한다. 새로고침 시 브라우저는 쿠키로 BFF의 로그인 상태를 확인하고 안전한 사용자·인증 상태만 받는다. 세션만으로 토큰 검증·현재 접근 자격 검사를 우회할 수 없으며, 자동 상태 확인·토큰 갱신은 사용자 활동으로 인정하지 않는다. 서비스 간 SSO는 각 BFF의 서버 간 로그인 연계로 제공하고 브라우저의 공유 Refresh 쿠키·직접 토큰 요청에 의존하지 않는다. 각 SaaS는 자신의 BFF를 담당한다. Passport BFF는 기존 FastAPI 프로세스 내에 구성할 수 있으며 상세 세션 저장·쿠키·CSRF·연계 계약은 API·DB 설계에서 정의한다.

**JWT Access Token 공통화:** FR-AUTH-008-01~04는 확정이다. Local·OIDC 인증 후 API에 사용하는 Passport 발급 토큰은 RFC 9068을 따른다. 외부 JWT Access Token을 검증할 경우에는 Passport의 OIDC 연동 경계에서 Provider별 토큰 프로파일·검증 설정·클레임 매핑을 적용하며 외부 토큰의 RFC 9068 준수를 가정하지 않는다. 공통 엔진을 사용해도 API 토큰 검증과 외부 인증 검증의 용도·신뢰 설정을 혼용하지 않는다. 공통 내부 인증 정보의 상세 필드·자료형 및 Provider별 매핑은 후속 설계하며, 외부 인증 출처·대상 테넌트·OIDC 설정·MFA 근거를 보존한다. JWT 검증 이후에도 로그인 유지·철회 상태와 최신 접근 자격 검사를 적용한다.

**FR-AUTH-010 결정 범위:** 별도 신원 JWT를 발급하지 않으므로 해당 토큰의 명칭·클레임·검증 규칙·유효기간·철회 정책은 추가 설계하지 않는다. 이는 Access Token에 `sub` 등 사용자 식별 정보를 포함하지 않는다는 의미가 아니다. Local·OIDC 인증 후 발급하는 Passport Access Token의 포맷·공통 검증·내부 인증 정보 변환은 FR-AUTH-008-01~04로 확정하며, 수용 범위는 Passport API와 Papyrus 등 연동 SaaS API로 확정한다. audience 등 구체적인 계약은 D-02에서 계속 정의한다.

**검증 예:** 올바른 자격 증명으로 인증 성공, 잘못된 자격 증명으로 실패, 차단 계정 접근 거부, 비밀번호 변경 이후 기존 인증 수단의 처리 정책 확인, 만료·변조된 JWT 거부.

**OIDC 설정 변경 반영(확정):** 발급자·클라이언트 ID 변경이나 설정 비활성화 등 인증 신뢰에 영향을 주는 변경 시, 변경된 설정에 근거한 해당 테넌트의 기존 OIDC 인증 근거를 즉시 무효화하고 후속 접근을 거부한다. 접근을 재개하려면 유효한 설정으로 다시 OIDC 인증을 수행해야 하며, 비활성화된 동안에는 해당 OIDC로 재로그인할 수 없다. 표시명·설명처럼 인증 신뢰에 영향을 주지 않는 변경은 기존 로그인을 유지한다. 독립적인 Local 인증이나 다른 테넌트의 인증 근거는 이 변경만으로 무효화하지 않는다. 해당 인증 근거에 연결된 Passport 로그인과 Passport 발급 Access/Refresh Token도 즉시 무효화한다. 이는 외부 발급자의 토큰 자체를 Passport가 철회한다는 의미가 아니다. 변경 유형의 상세 분류, 즉시 무효화를 보장하는 설정 버전·캐시 검증 및 동시성 처리 방식은 후속 설계한다.

**인증 컨텍스트:** Passport와 SaaS는 인증 방식(Local/OIDC)과, OIDC인 경우 검증된 테넌트·OIDC 설정의 연관성을 신뢰할 수 있는 계약으로 확인해야 한다. Passport 자체 토큰의 발급자와 원본 외부 인증 발급자를 구분하고, 검증된 인증 방식·대상 테넌트·OIDC 설정·MFA 근거를 토큰 또는 서버 상태와 연결하여 확인한다. 외부 토큰에 Passport의 tenant_id가 포함된다고 가정하지 않으며, 동일 User·동일 이메일·다른 테넌트 멤버십만으로 OIDC 인증 결과의 적용 범위를 확장하지 않는다. 전역 User와 `(issuer, subject)` 기반 신원 식별은 유지하되, 신원 연결과 대상 테넌트의 인증 요건 충족을 구분한다.

**서비스 간 SSO(확정):** 같은 테넌트에서 Passport 관리 포털 또는 Papyrus 등 연동 SaaS에 외부 OIDC로 로그인한 사용자는 다른 서비스로 이동할 때 아이디·비밀번호를 다시 입력하지 않고 이용할 수 있어야 한다. 정책상 필요한 MFA 및 재인증은 별도로 적용하며, 대상 테넌트의 현재 멤버십·서비스 이용 자격 검증은 유지한다. API 인증에는 Passport 발급 Access Token을 사용하며 API별 audience와 기존 OIDC 인증 범위를 유지한다.

**중요:** 외부 OIDC의 **ID Token**은 Passport가 로그인 결과를 검증하기 위한 토큰이며 API용 Bearer 토큰으로 사용하지 않는다. Passport는 검증된 외부 인증과 테넌트 정책을 근거로 자체 Access Token을 발급하고, Passport API와 연동 SaaS API는 Passport 서명·자신의 `aud`·현재 접근 자격을 검증한다. 외부 Provider가 Papyrus용 Access Token을 직접 발급할 필요는 없다. API별 Passport 토큰 발급과 서비스 간 로그인 상태·인증 컨텍스트 연계 방식은 **후속 설계 사항**이다.

**OIDC 로그인 생명주기:** Passport 발급 Refresh Token으로 자체 Access Token을 갱신하며 FR-AUTH-009의 로그인 유지 한도·회전·재사용 탐지·즉시 철회를 적용한다. 외부 계정 차단·Provider 로그아웃·외부 토큰 철회가 Passport 로그인과 자체 토큰에 자동 전파된다고 가정하지 않는다. 외부 계정 차단·비활성화를 신뢰할 수 있는 방식으로 확인한 뒤에는 FR-OIDC-015에 따라 해당 외부 신원에 근거한 해당 테넌트의 Passport 로그인 전체와 Access/Refresh Token을 즉시 무효화한다. 독립적인 Local 로그인과 다른 테넌트 로그인은 이 조치만으로 종료하지 않는다. 정상 연동 시 사용 중인 OIDC 로그인의 차단·비활성화 감지 목표는 상태 변경 후 최대 5분이다. 외부 상태 확인 불가 시에는 FR-OIDC-016에 따라 기존 Access Token의 남은 유효기간까지 접근을 허용하되 신규 OIDC 로그인·토큰 갱신을 거부한다. Provider 로그아웃의 사실과 대상을 신뢰할 수 있게 확인한 뒤에는 FR-OIDC-017에 따라 해당 테넌트에서 대상 외부 로그인에 연결된 Passport 로그인·Access/Refresh Token을 즉시 무효화한다. Passport에서 현재 로그인 또는 모든 기기를 로그아웃할 때는 FR-AUTH-009-04에 따라 Passport 로그인·토큰만 종료하고 외부 Provider 로그아웃은 요청하지 않는다. 이후 새 OIDC 로그인은 외부 로그인 상태에 따라 자격 증명 재입력 없이 진행될 수 있으나, 새 로그인 트랜잭션 검증과 현재 접근 조건 검사는 유지한다. 감지 수단·Provider별 목표 달성 가능성, 로그아웃 통지 지원·검증·대상 매핑·전달 지연, 외부 토큰의 명시적 철회 감지·검증·대상 매핑·전달 지연과 재인증 조건은 구현 전 후속 설계에서 검증·결정한다. 외부 토큰의 보안상 명시적 철회 사실과 대상을 확인한 경우에는 FR-OIDC-018에 따라 해당 테넌트에서 철회 대상 인증에 연결된 Passport 로그인·토큰을 즉시 무효화하며, 정상적인 외부 토큰 만료·교체는 이 조항에 따른 종료 사유로 사용하지 않는다. Local·OIDC 인증 후 발급하는 Passport Access Token은 모두 30분 유효·서명키 90일 자동 교체를 적용하며, 키 배포·전환 및 긴급 대응의 상세는 D-02·D-09에서 설계한다.

**OIDC 최초 계정 생성(확정):** 기존 Passport 계정이 없는 사용자가 대상 테넌트의 OIDC 설정에 따른 외부 인증에 성공하면, Passport 사용자 계정과 `(issuer, subject)` 기반 외부 신원 연결을 자동 생성한다. 별도의 Local 회원가입을 요구하지 않는다. 동일 이메일이라는 이유로 기존 계정에 자동 연결하지 않는 원칙은 유지한다. 기존 계정에 외부 신원을 추가할 때는 기존 Passport 계정 재인증과 연결할 외부 OIDC 인증을 모두 완료하고 사용자가 명시적으로 연결을 확인해야 하며, 플랫폼 관리자 승인은 요구하지 않는다. 최초 OIDC 인증 시 동일 이메일의 기존 Passport 계정이 있으면 새 계정을 생성하지 않고 기존 계정 재인증 후 명시적으로 연결하도록 안내한다. 연결하려는 외부 신원이 이미 다른 Passport 사용자에게 연결되어 있으면 새 연결 요청을 거부하고 기존 연결을 유지한다. 계정 병합과 외부 신원의 계정 간 이전은 이번 범위에서 제공하지 않는다. 사용자 계정 생성과 테넌트 멤버십 부여는 구분한다. 최초 OIDC 인증 시 테넌트 소속 부여 방식은 테넌트별로 설정하며, 테넌트 관리자가 일반 구성원 자동 등록 또는 관리자 사전 등록·초대 방식 중 선택한다. 새 테넌트의 기본값은 관리자 사전 등록·초대이며, 자동 등록은 테넌트 관리자가 명시적으로 활성화해야 한다.

**PII 최소화:** 초기 서비스는 대한민국과 해외 고객을 함께 대상으로 설계한다. 초기 지원 국가·지역은 대한민국, 미국, 일본, 대만, 캄보디아, 베트남, 태국, 러시아, 말레이시아, 인도네시아, 필리핀, 캐나다, 싱가포르로 확정한다. 초기에는 일반 기업의 공통 인증·계정·테넌트 관리 및 개인정보 보호 요구사항을 우선하며, 특정 업종의 추가 요건은 후속 범위로 둔다. 필수 프로필 항목은 이메일과 표시 이름이며 표시 이름은 실명일 필요가 없다. 실명·전화번호는 필수로 요구하지 않는다. 선택 프로필 항목은 프로필 사진·전화번호·실명으로 확정한다. 테넌트 관리자는 자신의 테넌트에서 정상 이용 중인 구성원이 입력한 실명·전화번호를 조회할 수 있다. 제품의 프로필 수집·이용 목적은 FR-USER-002-01로 확정한다. 정상 계정의 역할별 프로필 열람 권한과 연동 SaaS 제공 필드는 FR-USER-002-02로 확정한다. 탈퇴 후 추가 보관 정보의 열람 범위는 FR-USER-005-01로 확정하며 최종 보존 정책은 별도 결정한다. 또한, 확정된 이용 목적을 포함한 최종 개인정보 처리 명세는 대상 국가·지역의 법령 검토를 반영한다. 패스워드, 외부 Access Token, 민감 개인정보는 로그에 기록하지 않는다.

**FR-MEM-007 결정 범위:** 외부 협력자에게도 기존 계정·테넌트·멤버십 관리 및 초대 정책을 적용한다. 유효한 Local 인증 또는 대상 테넌트의 OIDC 인증, 현재 멤버십, MFA 및 서비스 이용 자격 검증을 충족해야 하며, 외부 협력자라는 이유로 인증·인가 예외를 허용하지 않는다. 일반 구성원과 외부 협력자 모두 D-07에 따라 테넌트 단위의 서비스 이용 자격을 적용하며, Passport에서 사용자별 별도 서비스 허가를 관리하지 않는다.

**개발 단계(확정):** OTP 기반 MFA는 최초 제품(P0)에 포함하며, 첫 출시부터 OTP 등록·인증·해제·분실 복구 및 테넌트별 설정을 제공한다. **OTP 방식(확정):** RFC 6238의 TOTP(시간 기반 OTP)를 지원한다. **기본값(확정):** 새 테넌트의 MFA는 비활성화이며, 권한 있는 관리자가 명시적으로 활성화해야 한다. **설정 권한(확정):** 테넌트 관리자는 자신의 테넌트 MFA 설정을 변경할 수 있고, 플랫폼 관리자는 전체 테넌트의 MFA 설정을 변경할 수 있다. **외부 MFA 인정(확정):** 외부 OIDC Provider의 MFA가 대상 테넌트 정책을 충족했음을 Passport가 검증할 수 있으면 추가 OTP를 생략하고, 확인할 수 없으면 Passport TOTP를 요구한다. **TOTP 등록 범위(확정):** 사용자·테넌트 조합 단위로 등록·관리하며, 같은 사용자도 테넌트마다 독립적인 TOTP를 각각 등록한다. MFA 정책 충족 여부는 대상 테넌트별로 검증한다. **MFA 완료 상태 유효기간(확정):** 해당 테넌트의 현재 로그인이 유효한 동안 완료 상태를 재사용하며, 새 로그인에서는 대상 테넌트의 MFA 정책 충족 여부를 다시 검증한다. 웹 최대 8시간·기타 사용자 클라이언트 최대 7일 및 미사용 만료 조건을 따른다. **분실 복구 방식(확정):** 일회용 복구 코드와 관리자 본인 확인 후 초기화를 모두 제공한다. 복구 코드는 사용자·테넌트별로 관리하고 기존 계정 인증과 함께 사용하여 TOTP를 재등록한다. **복구 권한(확정):** 테넌트 관리자는 자신의 테넌트의 다른 구성원을, 플랫폼 관리자는 전체 테넌트의 다른 사용자를 대상으로 본인 확인 후 TOTP 복구 초기화를 수행할 수 있다. **관리자 복구 본인 확인(확정):** 사용자 계정 재인증(Local 비밀번호 또는 대상 테넌트 OIDC Provider 재인증)과 관리자의 사전에 확인된 조직 연락 경로·대면 등을 통한 별도 본인 확인을 모두 요구한다. 기존 복구 권한 범위 내에서 초기화·재등록을 진행하고 처리자·대상·사유를 감사 기록에 남긴다(FR-MFA-004-02). **개인 OTP 해제(확정):** 계정 재인증과 해당 사용자·테넌트의 현재 OTP 검증을 모두 요구한다. Local은 비밀번호 재확인, OIDC는 대상 테넌트 Provider 재인증을 적용하며 기존 로그인 상태만으로 대체하지 않는다. 분실 시 기존 복구 절차를 사용하며 테넌트의 MFA 활성화 설정은 유지한다(FR-MFA-004-01). **MFA 활성화 반영 시점(확정):** 활성화 전에 이미 유효한 로그인은 기존 유효기간까지 유지하며, 새 로그인부터 MFA를 적용한다. 토큰 갱신으로 기존 로그인 유지 한도를 연장하지 않는다. 등록 및 기타 설정 변경의 상세 절차와 개인 OTP 해제·관리자 복구의 API·UI 세부 계약은 후속 설계한다. Provider별 MFA 근거·정책 매핑과 SaaS의 전달·검증 계약은 후속 설계한다. 외부 OIDC에 MFA를 적용할 때도 검증된 외부 MFA 또는 Passport TOTP 결과와 대상 테넌트의 연관성을 보존한 뒤 Passport 자체 Access Token을 발급한다. 자체 토큰 발급으로 미충족 MFA 정책을 우회하지 않는다.

## 5. 인가(Authorization) 모델

인가는 다음 순서의 **독립된 검사**로 정의한다.

1. **인증 신뢰성:** Access Token이 유효하며 Passport에 매핑된 사용자 신원인가?
2. **테넌트 인증 요건:** 유효한 Local 인증인가, 또는 대상 테넌트의 OIDC 설정으로 검증된 유효한 인증인가?
3. **계정 유효성:** 사용자 계정이 활성화되어 있는가?
4. **테넌트 소속:** 요청한 `tenant_id`에 대한 현재 멤버십이 유효한가?
5. **서비스 이용 계약:** 해당 `tenant_id`에서 대상 `Application`이 활성화되어 있는가?
6. **도메인 권한:** Papyrus가 요청 리소스에 대한 읽기/쓰기 등을 허용하는가?

**MFA 적용 검증(확정):** MFA가 활성화된 테넌트는 서비스 접근을 허용하기 전에 해당 테넌트의 MFA 정책 충족 여부를 추가로 확인한다. 단, 활성화 시점에 이미 유효한 로그인은 기존 로그인 유효기간까지 MFA 추가 요구를 유예하며, 새 로그인부터 적용한다. 정책 충족을 검증할 수 있는 외부 OIDC MFA 결과는 인정하며, 확인할 수 없으면 Passport TOTP를 요구한다. 구체적인 인증 결과 전달·검증 계약은 후속 설계한다.

**보안 불변 조건**

- 클라이언트의 `tenant_id`는 **선택자**일 뿐 권한 증명이 아니다. 서버가 항상 인증된 사용자와 현재 멤버십을 대조한다.
- 외부 OIDC 인증에서 대상 테넌트와 검증된 OIDC 설정의 연관성을 확인한다. 다른 테넌트의 OIDC 인증 결과나 사용자 신원 연결만으로 대상 테넌트 접근을 허용하지 않는다. 유효한 Local 인증에 의한 테넌트 선택은 별도로 허용한다.
- 모든 테넌트 범위 조회·수정은 `tenant_id` 범위 또는 동등한 강제 경계를 적용한다.
- `user_id`와 `tenant_id`는 유일하고 임의 추측하기 어려운 식별자로 설계한다. 식별자 난수성만으로 인가를 대체하지 않는다.
- 플랫폼 관리자 기능은 일반 테넌트 API와 분리하여 강한 인증, 최소 권한, 감사 기록을 적용한다.
- JWT의 이전 멤버십 클레임이나 변경 전의 허용 캐시만으로 현재 접근 자격을 보장하지 않는다. FR-APP-008-01의 변경 API 성공 응답 이후 신규 요청 차단을 보장하는 상태 검증·캐시 무효화 정책을 정의한다.

## 6. 주요 데이터 모델 (논리 ERD)

이 절은 엔터티와 관계의 초기 논리 모델이다. 실제 테이블·컬럼·제약·인덱스와 인증 상태 저장 구조는 11장의 Phase 1 DB 모델 설계에서 구체화한다.

| 엔터티                  | 주요 속성(예시)                                      | 핵심 제약                          |
| ----------------------- | ---------------------------------------------------- | ---------------------------------- |
| `User`                  | `id`, `status`, `created_at`                         | 전역 불변 ID                       |
| `UserProfile`           | `user_id`, `display_name`, `email`, `avatar_ref`, `phone`, `real_name` | 이메일·표시 이름 필수, 프로필 사진·전화번호·실명 선택, PII 보호 |
| `Identity`              | `user_id`, `provider_type`, `issuer`, `subject`      | 외부 신원 `(issuer, subject)` 유일 |
| `Credential`            | `user_id`, `password_hash`, `updated_at`             | 안전한 해시, 접근 최소화           |
| `Tenant`                | `id`, `name`, `status`, `access_version`             | 전역 불변 ID, 테넌트 접근 자격 변경 버전 |

| `TenantApplication`     | `tenant_id`, `application_id`, `status`, `access_version` | 테넌트-서비스 관계 고유, 서비스 이용 관계 변경 버전 |
| `AuditEvent`            | `actor_id`, `tenant_id`, `action`, `target_id`, `at` | 변경 추적, PII 최소화              |

```mermaid
    USER ||--o{ IDENTITY : authenticates_with
    USER ||--o| CREDENTIAL : local_credentials
    USER ||--o{ TENANT_MEMBERSHIP : belongs_to
    TENANT ||--o{ TENANT_MEMBERSHIP : has

    TENANT ||--o{ TENANT_APPLICATION : subscribes

```

**모델링 주의:** `User`의 이메일과 외부 Provider 이메일은 신원 유일성을 판단하는 단독 키가 아니다. 하나의 User에 여러 인증 수단을 연결할 수 있다. `Tenant`는 논리적인 고객 조직을 나타내며 법인·회사와 일대일 관계를 강제하지 않는다. 같은 회사의 여러 테넌트도 각각 독립적으로 관리한다. `Organization`과 `Tenant`의 별도 분리는 현재 요구하지 않는다.

**OIDC 설정 격리:** 테넌트별 OIDC 설정과 로그인 트랜잭션은 독립 관리한다. 설정이 없거나 비활성인 테넌트의 OIDC 로그인은 허용하지 않는다. 같은 OIDC 제품을 사용하더라도 설정과 검증 범위를 테넌트별로 구분하며, issuer 하나만으로 대상 테넌트의 인증 요건 충족을 판단하지 않는다. Local 인증 및 전역 User·테넌트 멤버십 모델은 유지한다.

## 8. 핵심 사용 시나리오 및 인수 기준

### SC-01 Local 가입 및 로그인

1. 사용자가 관리자 초대나 승인 없이 Passport에 Local 계정 공개 가입을 요청한다.
2. Passport가 계정·자격 증명을 등록하며, 이메일 소유 확인 전에는 이메일 인증·재발송 등 가입 완료에 필요한 기능만 허용한다.
3. 사용자가 인증 링크나 코드로 이메일 소유 확인을 완료한다. 구체적인 확인 수단·유효기간·재발송 제한은 후속 설계한다.
4. 사용자가 정상적인 자격 증명으로 로그인한다.
5. Passport가 유효한 Local JWT Access Token을 발급한다. 웹에서는 BFF가 Access/Refresh Token을 서버에 보관하고 브라우저에는 로그인 세션 쿠키와 안전한 상태만 제공한다.
6. 사용자가 소속 테넌트를 선택하고, 계정·테넌트·멤버십·MFA·서비스 이용 자격 검증 후 접근한다.

**인수 기준:** 이메일 소유 미확인 Local 계정은 일반 API 및 SaaS 이용이 거부되고, 이메일 인증·재발송 등 가입 완료에 필요한 기능만 허용됨. 이메일 확인 완료 후에도 테넌트 소속 및 SaaS 이용 권한은 별도로 검증됨. 잘못된 비밀번호 또는 비활성 사용자일 때 인증 실패. 비밀번호 원문 미저장. 발급 토큰의 만료·서명·발급자 검증 성공. Local 로그인 응답에 별도 신원 JWT 또는 OIDC ID Token을 발급하지 않으며, 인증된 현재 사용자 조회 API로 사용자 정보를 제공함. Local 인증 사용자는 대상 테넌트의 OIDC 인증 없이 소속 테넌트를 선택할 수 있으나, 멤버십·MFA·서비스 이용 자격 검증을 우회할 수 없음.

### SC-02 외부 OIDC 로그인

1. 사용자가 테넌트 전용 로그인 링크로 접속하거나 공통 로그인 화면에서 테넌트 코드를 입력하여 대상 테넌트를 식별한다.
2. Passport는 해당 테넌트의 활성 OIDC 설정으로 인증을 시작하고, 로그인 트랜잭션에 테넌트·설정을 연결한다.
3. 사용자는 해당 테넌트의 OIDC 서비스에서 인증한다.
4. Passport는 시작 시 연결한 테넌트·설정을 기준으로 응답과 흐름별 필수 클레임·토큰을 검증한다.
5. `(issuer, subject)`를 기준으로 Passport User와 매핑한다. 기존 Passport 계정이 없는 사용자는 별도의 Local 회원가입 없이 사용자 계정과 외부 신원 연결을 자동 생성한다. 기존 계정과의 연결·충돌은 D-08 정책을 따른다.
6. 해당 테넌트의 현재 멤버십·MFA·서비스 이용 자격을 검증한다.
7. Passport가 대상 테넌트·허용된 API 범위의 자체 JWT Access Token과 Passport Refresh Token을 발급한다. 외부 인증 출처·OIDC 설정·MFA 근거는 보존한다.
8. 웹은 토큰을 BFF 서버에 보관하고 브라우저에 로그인 쿠키와 안전한 상태만 제공한다. BFF가 사용자 Access Token으로 Passport·연동 SaaS API를 호출하며, 각 API는 토큰 및 현재 접근 자격을 검증한다. 직접 API 클라이언트는 기존 토큰 방식을 따른다.

**인수 기준:** 테넌트 전용 링크와 공통 화면의 테넌트 코드 입력 모두 대상 테넌트의 설정에 따른 OIDC 로그인을 시작할 수 있음. 신규 외부 신원의 이메일이 기존 Passport 계정과 같으면 새 계정을 생성하거나 자동 연결하지 않고 기존 계정 재인증 후 명시적 연결을 안내함. 대상 테넌트에 설정되지 않은 발급자, 잘못된 서명·nonce·audience, 테넌트·설정·Callback 변조 및 계정 연결 충돌을 거부. 동일 이메일만으로 자동 병합하지 않음. OIDC 설정 누락·비활성·오류 시 다른 테넌트나 플랫폼 공통 Provider로 자동 대체하지 않음. 인증·접근 조건을 충족한 경우에만 Passport 발급 Access/Refresh Token을 발급하며, 잘못된 외부 인증·미충족 MFA·이용 자격으로 API 접근용 토큰을 발급하지 않음. 외부 원본 토큰의 직접 API 사용과 OIDC 기반 자체 토큰의 다른 테넌트 사용을 거부함. OIDC 신뢰 설정 변경 시 연결된 Passport 로그인·Access/Refresh Token이 즉시 무효화됨. 외부 계정 차단·비활성화 확인 시 해당 외부 신원에 근거한 해당 테넌트의 로그인 전체와 Access/Refresh Token이 즉시 무효화되고, 만료 전 Access Token도 후속 API 요청에서 거부됨. 독립적인 Local 로그인과 다른 테넌트 로그인은 이 조치만으로 종료되지 않음. Provider 정상 연동 조건에서 사용 중인 OIDC 로그인의 차단·비활성화 상태 변경부터 감지까지 최대 5분 목표를 검증함. 외부 상태 확인 불가 시 기존 Access Token은 다른 접근 조건을 충족하는 동안 남은 유효기간까지만 수용하며, 신규 OIDC 로그인·토큰 갱신과 만료·철회·차단된 토큰의 사용을 거부함(FR-OIDC-016). 외부 Provider 로그아웃의 사실과 대상을 검증하면 해당 테넌트의 연결된 Passport 로그인·Access/Refresh Token이 즉시 무효화됨. 잘못된 로그아웃 근거는 거부하며 독립적인 Local 로그인과 다른 테넌트 로그인은 종료하지 않음(FR-OIDC-017). Passport의 현재 로그인 및 모든 기기 로그아웃은 선택한 범위의 Passport 로그인·토큰을 종료하며 외부 Provider 로그아웃을 요청하지 않음(FR-AUTH-009-04). 외부 토큰의 보안상 명시적 철회 사실과 대상을 검증하면 해당 테넌트에서 연결된 Passport 로그인·토큰이 즉시 무효화됨. 잘못된 철회 근거는 거부하며, 정상적인 외부 토큰 만료·교체만으로는 이 조항에 따라 종료하지 않음(FR-OIDC-018).

### SC-03 전역 테넌트와 서비스 활성화

1. 이메일 소유 확인을 완료한 사용자 `U-100`이 플랫폼 관리자 승인 없이 `T-100` 테넌트를 생성한다.
2. Passport가 생성자 `U-100`을 `T-100`의 첫 관리자로 자동 등록한다.
3. `T-100`에서 Papyrus 이용을 활성화한다.
4. Papyrus는 `T-100`을 그대로 참조한다.

**인수 기준:** 이메일 소유 확인을 완료한 사용자는 플랫폼 관리자 승인 없이 Passport에서 새 테넌트를 생성할 수 있음. 생성자는 해당 테넌트의 첫 관리자로 자동 등록되며 해당 테넌트의 구성원·설정을 관리할 수 있으나, 테넌트 생성으로 플랫폼 관리자 권한을 얻지 않음. Passport와 Papyrus의 `tenant_id`가 일치. 서비스 활성화 전에는 접근 불가. 별도 Application Tenant가 생성되지 않음.

### SC-04 동일 사용자의 복수 테넌트 접근

1. `U-100`이 `T-100`, `T-200` 모두에 소속된다.
2. 사용자가 활성 테넌트를 선택한다.
3. Local 인증 사용자는 유효한 Local 인증으로 테넌트를 선택할 수 있다. OIDC 인증 사용자는 대상 테넌트의 유효한 OIDC 인증 결과가 없으면 해당 테넌트의 OIDC 로그인 또는 별도의 Local 로그인이 필요하다.
4. 각 요청에서 선택된 테넌트에 대한 인증 요건 및 현재 멤버십을 검증한다.

**인수 기준:** 허가된 테넌트만 접근 가능. 단순 URL/헤더의 테넌트 ID 변경으로 권한 상승 불가. `T-100`의 OIDC 인증만으로 `T-200`에 접근할 수 없음. 동일 User에 외부 신원이 연결되어 있거나 양쪽 멤버십이 있더라도 이 조건을 우회할 수 없음. 유효한 Local 인증 사용자는 대상 테넌트의 멤버십 등 접근 조건 충족 시 두 테넌트를 선택하여 접근 가능.

### SC-05 멤버십 해지와 SaaS 접근 차단

1. 테넌트 관리자가 사용자의 멤버십을 해지한다.
2. Passport의 멤버십이 비활성화된다.
3. 변경 API가 성공 응답을 반환한 뒤 시작되는 Papyrus의 해당 테넌트 범위 신규 API 요청부터 거부한다.

**인수 기준:** 변경 API 성공 응답 이후 시작된 해당 범위의 신규 API 요청은 즉시 거부된다. 변경 전의 허용 캐시나 유효한 Access Token이 남아 있어도 접근할 수 없다. 테넌트 중지·비활성화와 테넌트의 특정 SaaS 이용 중단에도 같은 기준을 적용한다. 변경 성공 응답 전에 이미 인가 검사를 통과하여 처리 중인 요청은 완료를 허용하며, 해당 변경만을 이유로 강제 중단·롤백하지 않는다. 장애로 접근 자격의 최신 상태를 확인할 수 없으면 요청을 차단하고 일시적인 검증 불가 오류를 반환한다. 이전 허용 캐시가 있어도 접근을 허용하지 않으며, 이 실패만으로 기존 로그인 상태·Refresh Token을 폐기하지 않는다. 접근 자격 캐시를 재사용하는 요청도 매번 Passport의 최신 여부 검증을 거쳐야 하며, 변경된 캐시로 접근을 허용하지 않고 현재 자격 정보를 다시 조회·검증한다.

**재가입 검증:** 관리자가 멤버십을 해지·비활성화한 사용자는 자동 등록 모드에서 유효한 OIDC로 다시 인증해도 멤버십이 복구되지 않아야 한다. 서비스 내 재가입 신청이 가능하며, 신청·승인 대기 중에는 접근이 거부되어야 한다. 해당 테넌트 관리자의 승인으로 멤버십을 복구한 후에도 공통 인증·계정·테넌트·MFA·서비스 이용 자격 검증을 충족해야 접근할 수 있다.

**버전 격리 검증:** 한 사용자의 멤버십 변경은 해당 사용자의 해당 테넌트 캐시에, 테넌트 상태 변경은 해당 테넌트의 모든 접근 자격 캐시에, 테넌트의 SaaS 이용 관계 변경은 해당 테넌트·SaaS의 접근 자격 캐시에 반영한다. 변경 버전이 일치하지 않는 캐시는 재사용하지 않으며, 관련되지 않은 사용자·테넌트·SaaS의 자격을 함께 무효화하지 않는다.

**트랜잭션 검증:** 접근 자격 상태와 관련 버전의 변경은 같은 DB 트랜잭션으로 커밋되어야 한다. 트랜잭션 실패 시 두 변경 모두 반영되지 않으며, 상태 또는 버전만 변경되는 부분 성공을 허용하지 않는다. 변경 API는 해당 커밋이 완료된 후 성공 응답을 반환한다.

**Valkey 버전 캐시 검증:** 변경 API의 성공 응답 이전에 DB의 관련 최신 버전이 Valkey 검증 경로에 반영되어야 한다. 늦게 도착한 이전 버전이나 복구 과정의 오래된 값이 최신 버전을 대체하여 접근을 허용하지 않는지 검증한다. DB 커밋과 Valkey 반영은 별도 처리 단계이며, Valkey 반영·최신성 검증이 완료되지 않은 상태를 변경 완료로 응답하지 않는다.

**DB 대체 검증:** Valkey를 사용할 수 없거나 그 버전의 최신성을 신뢰할 수 없을 때 DB의 현재 커밋된 상태·버전으로 직접 검증하는지 확인한다. DB에서 접근 자격이 유효한 경우에는 요청을 허용하고, 자격 회수가 확인되면 거부한다. DB 검증도 실패하면 이전 캐시로 허용하지 않고 일시적인 검증 불가 오류를 반환하며, 이 실패만으로 기존 로그인 상태·Refresh Token을 폐기하지 않는다.

**부분 실패·재시도 검증:** DB 커밋 후 Valkey 반영 실패를 유도했을 때 DB 상태·버전이 유지되고, 저장 완료·Valkey 반영 미완료를 구분한 일시적인 오류가 반환되는지 확인한다. 동일 요청을 재시도해도 DB 상태 변경과 버전 갱신이 중복 적용되지 않아야 한다. 재시도는 최신 DB 상태·버전을 기준으로 Valkey를 동기화하며, 뒤이어 발생한 다른 변경을 이전 상태·버전으로 되돌리지 않아야 한다. 변경 완료 응답은 Valkey 반영과 검증 경로의 최신성 보장을 완료한 뒤에만 반환한다.

### SC-06 계정 탈퇴

1. 사용자가 탈퇴를 요청한다.
2. 재인증 등 필요한 확인을 수행한다.
3. 사용자가 탈퇴를 확정하면 유예기간 없이 즉시 탈퇴를 완료하고 계정·인증 수단·멤버십의 효력을 종료한다. 탈퇴 취소 및 기존 계정 복구는 제공하지 않는다.
4. 개인정보는 승인된 보존·삭제 정책에 따라 처리한다.

**인수 기준:** 본인 확인 후 탈퇴 확정 시 유예기간 없이 탈퇴가 완료되고, 탈퇴 취소·기존 계정 복구가 제공되지 않음. 탈퇴 이후 무단 재로그인 및 이전 소속으로의 접근 불가. 개인정보 삭제·보존 시점은 별도 승인된 정책을 따르며 데이터 보존/삭제 조치가 추적 가능. 허용된 추가 보관 기간 내 정보는 승인된 목적에 한해 플랫폼 관리자와 탈퇴 시점 소속 테넌트의 현재 권한 있는 관리자가 조회하며 조회자·대상·사유가 감사 기록에 남음. 일반 구성원·연동 SaaS와 무관한 테넌트·현재 권한 없는 사용자의 조회 및 보관 기간 종료 후 조회는 거부됨(FR-USER-005-01).

### SC-07 테넌트별 OTP MFA 적용

1. 권한 있는 관리자가 `T-100`의 MFA를 활성화하고 `T-200`의 MFA는 비활성화한다.
2. 두 테넌트에 소속된 사용자가 MFA 활성화 후 새 Local 로그인 또는 `T-100`에 설정된 새 OIDC 로그인으로 `T-100`에 접근하면 해당 테넌트의 MFA 정책 충족 여부를 검증한다. 외부 Provider의 MFA 완료로 정책 충족을 검증할 수 있으면 추가 OTP를 생략하고, 확인할 수 없으면 Passport TOTP를 요구한다.
3. 사용자가 테넌트를 전환하면 대상 테넌트의 MFA 설정과 인증 충족 여부를 확인한다.

**인수 기준(권장):** MFA 활성화 후 성립한 새 로그인의 경우 `T-100`은 정책 충족을 검증한 외부 OIDC MFA 또는 유효한 Passport TOTP 인증 완료 전 접근이 거부되며, MFA 정책 충족 후 나머지 접근 조건을 검증하여 접근할 수 있다. 활성화 시점에 이미 유효한 로그인은 기존 유효기간까지 MFA 추가 요구가 유예되며, 계정·테넌트·멤버십·서비스 이용 자격 검사는 계속 적용된다. 토큰 갱신으로 이 유예나 기존 로그인 유지 한도를 연장하지 않는다. 잘못되거나 만료·재사용된 OTP는 거부된다. `T-100`의 설정 변경은 `T-200`의 설정을 변경하지 않으며, `T-200`에서의 인증만으로 `T-100`의 MFA 검증을 우회할 수 없다.

**개인 OTP 해제 인수 기준(확정):** 계정 재인증과 대상 사용자·테넌트의 현재 OTP 검증을 모두 완료한 경우에만 개인 TOTP 등록을 해제할 수 있다. 계정 재인증 누락·실패, 잘못되거나 만료·재사용된 OTP, 다른 테넌트의 OTP 및 기존 로그인 상태만을 근거로 한 해제는 거부한다. 해제 후에도 테넌트의 MFA 활성화 설정은 유지한다(FR-MFA-004-01).

**관리자 OTP 복구 인수 기준(확정):** 사용자 계정 재인증과 관리자의 별도 본인 확인을 모두 완료하고 기존 복구 권한을 충족한 경우에만 대상 사용자·테넌트의 TOTP를 초기화할 수 있다. 어느 한 확인의 누락·실패 및 권한 밖 초기화는 거부한다. 초기화 후 재등록을 요구하며 처리자·대상·사유에 대한 감사 기록, 테넌트 MFA 설정과 다른 테넌트 등록의 유지가 확인된다(FR-MFA-004-02).

## 10. 개발 아키텍처 및 리포지토리 구조

### 10.1 현재 리포지토리 구조

아래 구조는 현재 리포지토리의 디렉터리와 파일을 기준으로 한다. Backend는 `apps/api/passport/`에 Python 패키지를 직접 배치한다. Frontend 영역인 `apps/web/`는 현재 빈 디렉터리이며, React + TypeScript 관리 포털의 세부 구조는 구현 시 정한다.

```text
passport/                              # 리포지토리 루트
├── apps/
│   ├── web/                           # Frontend 영역, 현재 빈 디렉터리
│   └── api/                           # Backend 프로젝트 루트
│       ├── passport/                  # Python import 패키지
│       │   ├── __init__.py
│       │   ├── py.typed
│       │   ├── main.py                # FastAPI 앱 팩터리 및 ASGI app
│       │   ├── server.py              # 서버 실행 진입점
│       │   ├── api/                   # HTTP 요청·응답 처리
│       │   ├── apps/                  # 업무 기능 및 지원 컴포넌트
│       │   │   ├── application/       # SaaS Application 정보
│       │   │   ├── authentication/    # Local/OIDC/MFA, Access Token·Refresh Token
│       │   │   ├── identity/          # 사용자·계정 생명주기
│       │   │   ├── tenant/            # 전역 테넌트·멤버십
│       │   │   ├── audit/             # 감사 기록
│       │   │   ├── cache/             # 캐시 연동
│       │   │   ├── notification/      # 알림 처리
│       │   │   └── background_job/    # 백그라운드 작업 연동
```

**구현 상태:** 현재 `main.py`는 `create_app()`과 ASGI `app`을 제공하며, `server.py`는 Uvicorn 실행 함수를 제공한다. 나머지 Backend 디렉터리는 대부분 초기 패키지 상태이다. 위 주석과 아래 책임 정의는 각 패키지에 구현할 역할이며, 업무 기능·DB 연결·Lifespan·의존성 공급이 이미 구현되었다는 의미는 아니다. SaaS 이용 관계 관리 기능의 세부 패키지 배치는 구현 시 정하며, D-07에 따라 사용자별 `ApplicationMembership` 모델은 이번 범위에서 도입하지 않는다.

| `passport/core/` | 여러 기능에서 공유하는 타입·예외·인증 컨텍스트 등 공통 정의를 관리한다. 개별 업무 절차나 외부 연동을 모으는 위치로 사용하지 않는다. |
| `passport/db/` | DB 연결·연결 풀·요청별 세션·트랜잭션 기반 구성을 관리한다. ORM 모델은 `db/models/`에 배치한다. |
| `passport/settings/` | 환경변수와 실행 환경별 설정을 관리한다. 테넌트별 OIDC 설정 등 런타임 업무 데이터는 해당 업무 기능과 DB 모델에서 관리한다. |
| `passport/utils/` | 특정 업무에 속하지 않는 작은 보조 함수를 관리한다. 인증·인가·테넌트 정책은 담당 업무 기능에 둔다. |
| `tests/`, `migrations/` | 각각 Backend 테스트와 DB 스키마 변경 이력을 관리한다. |

### 10.3 구현 원칙

1. Backend는 하나의 배포 가능한 Modular Monolith로 시작하며, 기능과 컴포넌트를 위 패키지 구조로 구분한다.
2. 주요 호출·의존 방향은 `api → apps → db/core`로 구성한다. `db`의 ORM 모델에서 업무 서비스를 호출하거나 `core`가 `api`·개별 업무 서비스에 역으로 의존하여 순환 관계를 만들지 않도록 한다.
3. 요청용 FastAPI `Depends()` 연결은 `api`에서 시작하고, DB 세션 공급이나 서비스 구성 함수는 해당 책임을 가진 모듈에 둔다. 모든 의존성을 하나의 공통 디렉터리로 모으도록 강제하지 않는다. 전역 가변 Singleton에 의존하지 않는다.
4. 앱 조립은 `main.py`에서 시작한다. Lifespan은 공유 자원의 시작·종료를 관리하도록 앱에 등록하며, 초기화·연결 코드가 커지면 별도 모듈로 분리할 수 있다. 별도 `bootstrap` 패키지는 현재 구조의 필수 요소가 아니다.
5. OIDC 검증 클라이언트 등 Stateless 컴포넌트와 DB 연결 풀은 프로세스별 Lifespan에 맞춰 생성·재사용·정리한다. DB 세션은 요청별로 공급·정리한다. 테넌트별 OIDC 설정·자격 증명·검증 컨텍스트를 구분하며, 실행 중 설정 변경은 D-06의 인증 신뢰 변경 시 즉시 무효화 정책을 충족하도록 반영하며, 이를 보장하는 설정 버전·캐시 검증·동시성 처리의 상세는 후속 설계한다.
6. SQLAlchemy ORM 모델은 `db/models/`에서 관리한다. 비밀번호 변경 후 전체 로그인 종료와 같은 업무 절차는 해당 `apps` 서비스에서 처리하며, ORM 모델에서 알림 발송이나 백그라운드 작업 실행을 직접 호출하지 않는다.
7. Frontend와 Backend는 Git Repository를 공유하지만 코드 경계와 빌드는 분리한다. 각 웹은 정적 Web과 자신의 `/bff` 경로를 같은 Origin에 배포하고 BFF에서 리소스 API를 호출한다. Passport BFF는 기존 FastAPI 프로세스의 라우터·서비스로 구성할 수 있으며 브라우저 쿠키 경계와 Bearer 리소스 API 경계는 분리한다. SaaS는 자신의 BFF를 담당하며 구체적인 경로·배포 구성은 API 설계에서 정의한다.
8. FastAPI OpenAPI를 API 계약의 기준으로 활용하고, Frontend TypeScript Client 자동 생성은 권장한다.
9. 현재 Backend 의존성에는 SQLAlchemy의 asyncio 지원과 PostgreSQL 드라이버인 psycopg가 등록되어 있다. 실제 DB 연결 설정·모델·마이그레이션은 후속 구현 대상이다.
10. `Authentication` 추상 클래스는 `apps/authentication`에서 인증 방식의 공통 계약을 정의하며, 호출부는 이 계약에 의존한다. Local·OIDC 구현과 향후 SAML 구현은 각 방식의 검증을 담당하고 공통 내부 인증 정보를 반환한다. JWT 검증이 필요한 구현은 FR-AUTH-008-02의 공통 JWT 검증 엔진을 재사용한다.

### 10.4 빌드 및 실행 구성

| 항목 | 현재 설정 |
| ---- | --------- |
| Python | `>=3.15`; `.python-version`은 `3.15` |
| 배포 프로젝트명 | `Passport-API` |
| Python import 패키지 | `passport` |
| 빌드 Backend | `uv_build` |
| 패키지 탐색 | `[tool.uv.build-backend]`의 `module-name = "passport"`, `module-root = ""`로 Backend 프로젝트 루트의 `passport/`를 지정 |
| CLI 진입점 | `[project.scripts]`의 `api = "passport.server:main"` |
| ASGI 진입점 | `passport.main:app` |
| 기본 로컬 실행 주소 | `http://127.0.0.1:8000` |

설치와 실행은 `apps/api/`에서 수행한다.

```sh
uv sync --locked
uv run api
```

개발 중 자동 재시작이 필요하면 같은 디렉터리에서 다음 명령을 사용한다.

```sh
uv run uvicorn passport.main:app --reload
```

소스 배포본과 wheel 빌드는 같은 디렉터리에서 `uv build`로 수행한다. 실행 후 API 문서는 `/docs`, OpenAPI 명세는 `/openapi.json`에서 확인한다.

## 11. 단계별 개발 범위 제안

개발 순서는 **API 계약 설계 → DB 모델 설계 → 기반 구성 구현 → 최소 제품 구현 → 운영 강화 → 필요 시 확장**으로 한다. Phase 번호는 작업 순서이며 요구사항의 우선순위 P0·P1·P2와 구분한다. 설계는 먼저 P0 범위를 대상으로 수행하고, P1·P2는 해당 기능 구현에 착수할 때 계약과 모델을 추가 설계한다. API 계약과 DB 모델은 상호 검토하여 정합성을 확인한 뒤 구현에 반영한다.

### Phase 0 — API 계약 설계 (P0 우선)

- 4장의 기능 요구사항과 8장의 사용 시나리오를 기준으로 P0 API 전체 목록과 요구사항 ID의 대응 관계를 작성한다. 7장의 경로 예시에서 누락된 API도 포함한다.
- 각 API의 HTTP 메서드·경로·호출 주체, 요청·응답 스키마와 예시, 필드 검증 규칙, 상태 코드·오류 코드, 목록 조회의 페이징·검색·정렬 계약을 정의한다.
- 인증 필요 여부, 플랫폼·테넌트 관리자와 일반 사용자의 권한, 테넌트 범위, MFA 단계별 허용 작업과 프로필 필드별 반환 범위를 정의한다.
- 브라우저→BFF의 세션·CSRF·안전한 응답 계약과 BFF→Passport·SaaS 리소스 API의 Bearer·토큰 발급·갱신 계약을 분리한다. 서비스 간 BFF 로그인 연계, 고정된 중계 경로·대상 및 종료 범위도 정의한다.
- Local·OIDC 로그인, 이메일 확인, OTP 등록·해제·복구, 토큰 발급·갱신·로그아웃·철회 및 SaaS 접근 자격 검증의 흐름을 정의한다. JWT 클레임·API별 audience와 인증 컨텍스트, 상태 변경의 동시성·재시도·부분 실패 계약도 포함한다.

**산출물:** `docs/API_CONTRACT.yaml` — API 목록, 요청·응답 스키마·예시, 인증·인가 및 오류 계약, 주요 흐름과 요구사항 대응표. 구현 시 설계 내용을 OpenAPI 3에 기반하여 생성한다.

### Phase 1 — DB 모델 설계 (P0 우선)

- 6장의 논리 모델과 Phase 0 API 계약을 기준으로 물리 ERD와 데이터 사전을 작성한다. 각 테이블의 컬럼·자료형·NULL 허용·기본값, PK·FK·유일성·CHECK 제약과 인덱스를 정의한다.
- 사용자·프로필·인증 수단, 테넌트·OIDC 설정·멤버십, 서비스·이용 관계·감사 기록을 설계한다. 로그인 상태·BFF 세션 연결·서버 측 토큰 보호 및 동시 갱신, Refresh Token 회전·철회, OIDC·SSO 로그인 트랜잭션, 이메일 확인, 사용자·테넌트별 TOTP와 복구 코드 등 요구사항 충족에 필요한 상태 저장 구조도 포함한다.
- 계정·멤버십 등의 상태 전이, 외부 신원 유일성, 테넌트 격리, 비밀값 보호, 탈퇴·보존·삭제 처리 및 복원 시 재적용할 상태의 저장·연결 방식을 정의한다.
- API별 조회·변경과 트랜잭션 경계, 동시성·중복 처리 방지, 접근 자격 버전과 캐시의 연결을 검토하고 초기 마이그레이션 계획을 작성한다. 모델 설계로 API 계약 변경이 필요하면 두 산출물을 함께 갱신한다.

**산출물:** `docs/DB_MODEL.md` — 물리 ERD, 데이터 사전, 제약·인덱스, 상태 전이·트랜잭션·데이터 생명주기, API·요구사항 대응 및 초기 마이그레이션 계획.

**완료 기준:** P0 API가 읽고 변경하는 데이터와 인증·접근 자격 상태를 모델에 대응시킬 수 있고, 무결성·격리·동시성·철회·삭제 요구사항을 어떻게 보장하는지 설명되어 있다. API 계약과 DB 모델의 정합성을 확인하여 ORM·마이그레이션 구현의 기준으로 사용할 수 있다.

### Phase 2 — 기반 구성 구현 (확정)

- `db/session.py`에 비동기 연결 코드 및 커넥션 풀링 구현.
- DB 세션은 FastAPI DI를 통해 요청별 `AsyncSession`으로 공급하고, 요청 종료 시 정리한다. 요청 간 세션을 공유하지 않으며, 커넥션 풀 크기와 연결 대기 타임아웃을 설정할 수 있도록 한다.
- DB 트랜잭션은 `apps`의 업무 서비스에서 유스케이스 단위로 경계와 커밋 책임을 관리하고, 예외 발생 시 롤백한다. 세션 공급 의존성은 자동 커밋하지 않으며, 접근 자격 상태와 관련 `access_version` 변경은 같은 트랜잭션에서 원자적으로 처리한다.
- Phase 1 설계에 따라 ORM 모델을 구현하고 `migrations/`에 Alembic 기반 DB 마이그레이션 설정 및 초기 마이그레이션 작성. ORM 공통 Base·메타데이터를 연결하고, 애플리케이션 실행용 DB 계정과 마이그레이션용 DB 계정을 분리한다.
- `settings/`에 OS 환경변수 `PASSPORT_CONFIG_PATH`로 지정한 `config.json` 파일의 전체 경로를 읽는 애플리케이션 설정 구현. 환경변수가 설정되지 않았거나 빈 값이면 Backend 프로세스의 현재 작업 디렉터리(CWD)에 있는 `config.json`을 기본 설정 파일로 사용한다.
- API와 Alembic은 동일한 설정 로더를 사용한다. 설정 파일을 읽을 수 없거나 JSON 형식·설정값 검증에 실패하면 명확한 오류와 함께 실행을 중단하며, 환경변수로 지정한 경로의 오류를 기본 경로로 대체하지 않는다.
- `core/`에 비동기 방식의 로깅 구현
- `main.py`에서 앱 Lifespan을 등록하여 DB 엔진·커넥션 풀·로깅 자원을 프로세스별로 초기화하고, 앱 종료 시 연결 정리 및 남은 로그 배출을 수행한다.

### Phase 3 — Passport 최소 제품 구현 (P0)

- Local 회원가입·로그인·비밀번호 변경·탈퇴 요청
- 사용자 식별 및 개인정보 기본 관리
- OTP 기반 MFA 등록·인증·해제·분실 복구, 테넌트별 MFA 설정 및 관련 관리 포털 UI
- 테넌트별 독립 OIDC 설정, Keycloak·Auth0 각각의 연동·검증·사용자 매핑 및 두 테넌트 이상의 설정·인증 격리 검증
- Local·OIDC 인증 후 Passport JWT Access Token 발급·검증 및 Refresh Token 갱신·철회 계약
- 기존 계정 재인증·외부 OIDC 인증 후 사용자 직접 신원 연결, 동일 이메일 충돌 처리 및 관련 관리 포털 UI
- Global Tenant 및 TenantMembership 관리
- Application, TenantApplication 등록·조회 및 서비스 활성 상태
- 인증/인가 경계, Cross-Tenant 보안 테스트
- 관리 포털 BFF의 세션·로그인·서버 측 토큰 보관·갱신·API 중계와 SaaS BFF 연동
- 기본 관리 포털: 로그인·내 계정·테넌트·멤버 관리
- 감사 로그 및 운영 기본 관측성
- Papyrus와의 최소 통합 시나리오 1개 E2E 검증

### Phase 4 — 정식 기업 운영 강화 (P1)

- 사용자 초대·수락·복구 플로우
- 테넌트 멤버십 재가입 신청·관리자 승인 기능 및 관련 UI
- 고도화된 계정 연결 관리, OIDC Provider 호환성 확대 및 테넌트별 설정 운영 고도화
- 비밀번호 초기화, 보안 이벤트 조회, 사용자·테넌트 상태 관리 UI
- 개인정보 열람·반출, 운영자 감사 조회
- 서비스 이용 종료, 변경 전파 및 운영 자동화
- 정량 성능·가용성 요구와 장애 복원 검증

### Phase 5 — 필요가 발생할 때만 확장 (P2)

- 고급 인증 정책, SCIM 연동, 세부 서비스 관리 위임
- 별도 중앙 정책 엔진과 연계(실제 요구가 발생한 경우)
- 서비스 테넌트 독립화는 **현재 범위 아님**. 별도 아키텍처 변경 결정 필요.

**OTP MFA 개발 단계:** OTP 기반 MFA 및 테넌트별 설정 지원은 최초 제품(P0)에 포함한다. 첫 출시부터 OTP 등록·인증·해제·분실 복구와 테넌트별 설정 및 관련 관리 포털 UI를 제공한다.

| **D-01** | 외부 OIDC 로그인 결과를 Papyrus에서 어떻게 사용할 것인가? | **발급 방식 확정:** Passport가 외부 OIDC 인증과 대상 테넌트의 접근 조건을 검증한 뒤 Passport 자체 JWT Access Token을 발급하고, Passport API와 연동 SaaS API는 이를 사용한다. 원본 외부 토큰의 직접 수용 결정은 폐기한다. **SSO 범위 확정:** 같은 테넌트 내 관리 포털과 연동 SaaS 간 아이디·비밀번호 재입력 없는 이동을 제공하며 필요한 MFA·재인증은 별도 적용한다. **초기 Provider 확정:** Keycloak·Auth0. **후속 설계:** 제품 버전·OIDC 지원 설정, 자체 토큰 발급과 SSO 로그인 상태 연계, 외부 인증 출처·테넌트·MFA 컨텍스트 전달, 외부 계정 차단·비활성화 감지 수단·Provider별 목표 달성 가능성, Provider 로그아웃 통지 지원·검증·대상 매핑·전달 지연 및 외부 토큰 명시적 철회 감지·검증·대상 매핑·전달 지연. **차단 감지 목표 확정:** 정상 연동 시 사용 중인 OIDC 로그인의 상태 변경 후 최대 5분 이내 감지. **차단 확인 후 처리 확정:** 해당 외부 신원에 근거한 해당 테넌트의 Passport 로그인 전체·Access/Refresh Token을 즉시 무효화하며 독립적인 Local·다른 테넌트 로그인은 종료하지 않는다(FR-OIDC-015). **상태 확인 불가 시 처리 확정:** 기존 Access Token의 남은 유효기간까지 접근을 허용하고 신규 OIDC 로그인·토큰 갱신은 거부하며, 다른 접근 조건과 기존 차단·철회는 계속 적용한다(FR-OIDC-016). **외부 로그아웃 반영 확정:** 사실과 대상을 검증하면 해당 테넌트에서 연결된 Passport 로그인·토큰을 즉시 무효화하고 독립적인 Local·다른 테넌트 로그인은 종료하지 않는다(FR-OIDC-017). **Passport 로그아웃 범위 확정:** 현재 로그인 및 모든 기기 로그아웃은 선택한 범위의 Passport 로그인·토큰만 종료하고 외부 Provider 로그아웃은 요청하지 않는다(FR-AUTH-009-04). **외부 토큰 명시적 철회 반영 확정:** 사실과 대상을 검증하면 해당 테넌트의 연결된 Passport 로그인·토큰을 즉시 무효화하며 정상적인 외부 토큰 만료·교체와 구분한다(FR-OIDC-018). 범용 RFC 8693 토큰 교환 서버는 초기 범위에 포함하지 않는다. **최우선** |
| **D-02** | Passport 발급 JWT Access Token을 어떤 API가 수용하는가? | **수용 범위 확정:** Passport API와 Papyrus 등 연동 SaaS API 모두 Local·OIDC 인증 후 Passport가 발급한 Access Token을 수용한다. 각 API의 audience 등 토큰 검증 및 현재 접근 자격 검증은 필수다. Passport 토큰의 RFC 9068 표준화 및 용도별 설정을 분리한 공통 JWT 검증 엔진·내부 인증 정보 변환은 확정(FR-AUTH-008-01~04). 구체적인 `issuer`·`audience` 값과 구성·발급 방식, 키 배포·전환 및 긴급 대응 상세, 철회 검증 계약, 인증 컨텍스트 필드 및 Provider별 매핑은 후속 설계. **외부 토큰 처리:** 외부 JWT 검증은 OIDC 연동 경계에 한정하고 opaque 검증 API 연동은 초기 제외한다(FR-OIDC-009). 별도 신원 JWT는 발급하지 않음(FR-AUTH-010) |
| **D-03** | 브라우저 인증·토큰 저장·전달 방법은? | **BFF 방식 확정:** 관리 포털과 SaaS 웹의 브라우저는 HttpOnly·Secure 로그인 세션 쿠키로 자신의 BFF를 호출한다. Access/Refresh Token은 BFF 서버에 보관·갱신하고 브라우저 메모리·웹 저장소·쿠키·응답에 전달하지 않는다. BFF→리소스 API와 직접 API 클라이언트는 Access Token을 사용한다. SameSite·CSRF 방어, 기존 로그인 유지 한도·활동·MFA·철회·복원 및 연계 세션 무효화를 적용한다. SaaS별 BFF·서버 간 SSO 연계를 사용하며 공유 Refresh 쿠키에 의존하지 않는다. 세션 저장·쿠키 세부 속성·중계 경로·서버 간 로그인 계약은 API·DB 설계에서 구체화한다. |
| D-04     | Local 사용자 가입 승인 및 이메일 확인 정책은?             | **가입 방식 확정:** 누구나 직접 Local 계정을 만들 수 있는 공개 가입을 제공한다. 관리자 초대나 승인은 요구하지 않으며, 테넌트 소속과 SaaS 이용 권한은 별도로 부여한다. **이메일 확인 확정:** Local 계정의 정상 이용 전 이메일 소유 확인은 필수이며, 확인 전에는 이메일 인증·재발송 등 가입 완료에 필요한 기능만 허용한다. 구체적인 확인 수단·유효기간·재발송 제한은 후속 설계한다. |
| D-05     | 테넌트 생성 권한과 의미는?                                | **생성 권한 확정:** 이메일 소유 확인을 완료한 사용자는 플랫폼 관리자 승인 없이 새 테넌트를 직접 생성할 수 있다. Passport가 전역 테넌트와 식별자의 권위 있는 원천이라는 책임은 유지한다. **최초 관리자 확정:** 테넌트 생성자를 해당 테넌트의 첫 관리자로 자동 등록하며 플랫폼 관리자 권한은 부여하지 않는다. **테넌트 의미 확정:** 논리적인 고객 조직으로 관리하며 법인·회사와 일대일 대응을 강제하지 않는다. 같은 회사도 운영 목적에 따라 여러 독립 테넌트를 가질 수 있다. |
| D-06     | 테넌트별 OIDC 설정 및 운영 세부 정책은?                    | 테넌트별 독립 설정과 해당 OIDC 서비스만 허용하는 외부 인증 정책은 확정(ADR-013, FR-OIDC-010~014, FR-TEN-009). Local 로그인 및 이후 테넌트 선택은 기존대로 유지. **활성 Provider 수 확정:** 테넌트당 한 번에 하나의 OIDC Provider만 활성화할 수 있다. **로그인 진입 방식 확정:** 테넌트 전용 로그인 링크와 공통 로그인 화면의 테넌트 코드 입력을 모두 지원한다. 구체적인 URL·코드 형식과 UI는 후속 설계한다. **설정 관리 권한 확정:** 테넌트 관리자는 자신의 테넌트 OIDC 설정을 플랫폼 관리자 승인 없이 등록·조회·변경·활성화·비활성화할 수 있으며, 플랫폼 관리자는 전체 테넌트의 설정을 관리할 수 있다. **설정 변경 반영 확정:** 발급자·클라이언트 ID 변경 또는 비활성화 등 인증 신뢰에 영향을 주는 변경은 해당 설정에 근거한 해당 테넌트의 기존 OIDC 인증 근거를 즉시 무효화하고 재인증을 요구한다. 비활성화된 설정으로는 재로그인할 수 없다. 표시명·설명 변경은 기존 로그인을 유지한다. 독립적인 Local 인증 및 다른 테넌트의 인증 근거는 이 변경만으로 무효화하지 않는다. 변경 유형의 상세 분류와 설정 버전·캐시 검증·동시성 처리는 후속 설계한다. |
| D-07     | 서비스 이용 자격은 테넌트 단위만 관리하는가?              | **확정:** SaaS 이용 자격은 `TenantApplication`으로 테넌트 단위로만 관리한다. 활성화된 서비스는 공통 인증·계정·테넌트·멤버십·MFA 검증을 충족하는 해당 테넌트의 모든 활성 구성원이 이용할 수 있다. 사용자별 별도 서비스 허가 및 `ApplicationMembership` 모델은 이번 범위에서 도입하지 않는다. 리소스별 권한은 각 SaaS가 관리한다. |
| D-08     | 가입자와 외부 신원 계정 연결 정책은?                      | **최초 계정 생성 확정:** 기존 Passport 계정이 없는 사용자는 대상 테넌트의 OIDC 인증 성공 시 사용자 계정과 `(issuer, subject)` 기반 외부 신원 연결을 자동 생성하며 별도의 Local 회원가입을 요구하지 않는다. 동일 이메일만으로 기존 계정에 자동 연결하지 않는다. **테넌트 소속 부여 확정:** 테넌트 관리자가 일반 구성원 자동 등록 또는 관리자 사전 등록·초대 방식 중 테넌트별로 선택한다. **기본값 확정:** 새 테넌트는 관리자 사전 등록·초대 방식을 기본으로 적용하며, 자동 등록은 테넌트 관리자가 명시적으로 활성화해야 한다. **재가입 처리 확정:** 관리자가 해지·비활성화한 기존 멤버십은 OIDC 재로그인만으로 자동 복구하지 않으며, 서비스 내 사용자 재가입 신청과 해당 테넌트 관리자 승인 후 복구한다. 승인 대기 중에는 접근을 허용하지 않는다. **기존 계정 연결(P0) 확정:** 최초 제품부터 연결 기능과 관련 모델·UI를 제공한다. 기존 Passport 계정 재인증과 연결할 외부 OIDC 인증을 모두 완료한 뒤 사용자가 명시적으로 확인하면 직접 연결한다. 플랫폼 관리자 승인은 요구하지 않는다. **동일 이메일 처리 확정:** 최초 OIDC 인증 시 동일 이메일의 기존 Passport 계정이 있으면 새 계정을 생성하지 않고 기존 계정 재인증 후 명시적 연결을 안내한다. **외부 신원 충돌 처리 확정:** 연결하려는 외부 신원이 이미 다른 Passport 사용자에게 연결되어 있으면 새 연결 요청을 거부하고 기존 연결을 유지한다. 계정 병합과 외부 신원의 계정 간 이전은 이번 범위에서 제공하지 않는다. **재가입 기능 개발 단계 확정:** 신청·승인 기능과 관련 UI는 기업 운영 강화 단계(P1)에 포함한다. OIDC 재로그인에 의한 자동 복구 금지와 기존 접근 차단 원칙은 P0에서도 적용한다. 전역 User 연결이 테넌트별 OIDC 인증 요건을 우회하지 않아야 한다. |
| D-09     | 로그인 유지·Refresh/Logout/철회는?                        | FR-AUTH-009-01~07 및 하위 항목의 정책은 확정. Passport의 현재 로그인 및 모든 기기 로그아웃은 선택한 Passport 로그인·토큰 범위에 적용하며 외부 Provider 로그아웃은 요청하지 않는다(FR-AUTH-009-04). 모든 클라이언트는 Access Token으로 API를 인증하고 Refresh Token으로 갱신한다. 웹 최대 8시간·미사용 30분, 모바일 등 최대 7일·미사용 3일, 백그라운드 자동 요청의 활동 제외, 현재/전체 로그아웃, 비밀번호 변경·재설정·계정 차단·비활성화 시 전체 로그인 종료, 종료 대상 Passport 발급 Access Token 즉시 철회 및 Refresh Token 매회 교체·재사용 탐지를 적용한다. Refresh Token 재사용 탐지 시 모든 Passport 관리 로그인 종료, Refresh Token 전체 폐기 및 기존 Passport 발급 Access Token 전체 즉시 철회도 확정(FR-AUTH-009-07-01). **Passport Access Token 수명 확정:** Local·OIDC 인증 후 발급하는 자체 토큰 모두 발급 후 30분. 로그인 유지·갱신·즉시 철회 정책은 Local·OIDC 로그인에 공통 적용하며, 외부 Provider 토큰의 수명과 구분한다. **서명키 교체 방식·주기 확정:** Local·OIDC 인증 후 발급하는 Passport Access Token 서명키는 모두 90일마다 자동 교체한다. 키 배포·전환 및 긴급 대응의 세부 계약은 후속 설계한다. 외부 계정 차단·비활성화 확인 후 관련 로그인·토큰의 즉시 무효화는 FR-OIDC-015로 확정한다. 정상 연동 시 사용 중인 OIDC 로그인의 차단·비활성화 감지 목표는 상태 변경 후 최대 5분이다. 외부 상태 확인 불가 시 기존 Access Token 만료까지 접근을 허용하고 신규 OIDC 로그인·토큰 갱신을 거부하는 정책은 FR-OIDC-016으로 확정한다. 검증된 외부 Provider 로그아웃 대상에 연결된 해당 테넌트 Passport 로그인·토큰의 즉시 무효화는 FR-OIDC-017로 확정한다. 검증된 외부 토큰의 보안상 명시적 철회 대상 인증에 연결된 해당 테넌트 Passport 로그인·토큰의 즉시 무효화는 FR-OIDC-018로 확정하며 정상적인 만료·교체와 구분한다. 감지 수단·Provider별 목표 달성 가능성, Provider 로그아웃 통지 지원·검증·대상 매핑·전달 지연, 외부 토큰 명시적 철회 감지·검증·대상 매핑·전달 지연과 Passport 갱신·재인증 연계, 연동 SaaS의 철회 상태 검증·반영 계약은 D-01~02에서, 토큰 저장·전달은 D-03의 확정 방식을 따르며 보안 세부 계약은 후속 설계한다. |

| D-12     | 테넌트별 OTP MFA의 세부 정책과 개발 단계는?                 | **개발 단계 확정:** 최초 제품(P0)에 OTP 등록·인증·해제·분실 복구, 테넌트별 설정 및 관련 관리 포털 UI를 포함한다. **OTP 방식 확정:** RFC 6238의 TOTP(시간 기반 OTP)를 지원한다. **기본값 확정:** 새 테넌트의 MFA는 비활성화이며, 권한 있는 관리자가 명시적으로 활성화하면 해당 테넌트 접근 시 MFA를 요구한다. **설정 권한 확정:** 테넌트 관리자는 자신의 테넌트 MFA 설정을, 플랫폼 관리자는 전체 테넌트의 MFA 설정을 변경할 수 있다. **외부 MFA 인정 확정:** 외부 Provider의 MFA가 대상 테넌트 정책을 충족했음을 검증할 수 있으면 Passport 추가 OTP를 생략하며, 확인할 수 없으면 Passport TOTP를 요구한다. Provider별 MFA 근거·정책 매핑과 SaaS의 전달·검증 계약은 후속 설계한다. **TOTP 등록 범위 확정:** 사용자·테넌트 조합 단위로 등록·관리하며, 같은 사용자도 테넌트마다 독립적인 TOTP를 각각 등록한다. MFA 정책 충족 여부는 대상 테넌트별로 검증한다. **MFA 완료 상태 유효기간 확정:** 해당 테넌트의 현재 로그인이 유효한 동안 재사용하며, 새 로그인에서는 대상 테넌트의 MFA 정책 충족 여부를 다시 검증한다. 웹 최대 8시간·기타 사용자 클라이언트 최대 7일 및 미사용 만료 조건을 따른다. **분실 복구 방식 확정:** 일회용 복구 코드와 관리자 본인 확인 후 초기화를 모두 제공한다. 복구 코드는 사용자·테넌트별로 관리하고 기존 계정 인증과 함께 사용하여 해당 테넌트의 TOTP를 재등록한다. **복구 권한 확정:** 테넌트 관리자는 자신의 테넌트의 다른 구성원을, 플랫폼 관리자는 전체 테넌트의 다른 사용자를 대상으로 본인 확인 후 TOTP 복구 초기화를 수행할 수 있다. **관리자 복구 본인 확인 확정:** 사용자 계정 재인증과 사전에 확인된 조직 연락 경로·대면 등을 통한 관리자 별도 본인 확인을 모두 요구하며, 기존 복구 권한 범위 내에서 초기화·재등록과 처리자·대상·사유 감사 기록을 적용한다(FR-MFA-004-02). **개인 OTP 해제 확정:** 계정 재인증(Local 비밀번호 재확인 또는 대상 테넌트 OIDC Provider 재인증)과 해당 사용자·테넌트의 현재 OTP 검증을 모두 요구한다. 기존 로그인 상태만으로 대체하지 않으며 OTP 분실은 기존 복구 절차를 사용하고 테넌트 MFA 활성화 설정은 유지한다(FR-MFA-004-01). **MFA 활성화 반영 시점 확정:** 활성화 전에 이미 유효한 로그인은 기존 유효기간까지 유지하며 새 로그인부터 MFA를 적용한다. 토큰 갱신으로 기존 로그인 유지 한도를 연장하지 않는다. 등록 및 기타 설정 변경의 상세 절차와 개인 OTP 해제·관리자 복구의 API·UI 세부 계약은 후속 설계한다. |

## 13. 개발 완료 판정 (Definition of Done)

- P0 API 계약서와 DB 모델 설계서가 작성되어 있고, 요구사항·API·데이터 모델·구현의 대응과 정합성이 확인되어 있다.
- P0 각 요구사항에 대해 API 계약, 오류 응답, 단위·통합 테스트가 연결되어 있다.
- 외부 OIDC와 Local 로그인 시나리오가 정상·실패 양쪽에서 검증된다.
- 추상 `Authentication` 클래스와 이를 상속한 Local·OIDC 구현이 공통 인증 계약을 충족하며, 향후 SAML 구현을 추가할 수 있는 구조로 구성된다(FR-AUTH-011).
- Local·OIDC 인증 후 Passport 자체 JWT Access Token이 발급되고 RFC 9068을 따른다. API는 Passport 발급 토큰만 수용한다. 외부 JWT는 Passport OIDC 연동 경계에서 용도별 설정으로 검증하며, 공통 내부 인증 정보에 외부 인증 출처·OIDC 설정·테넌트 범위·MFA 근거가 보존된다.
- 서로 다른 두 테넌트의 독립 OIDC 설정·로그인·Callback·토큰 검증이 격리되며, 다른 테넌트의 OIDC 인증 결과를 재사용하는 접근은 거부된다.
- Local 인증 사용자는 기존과 동일하게 소속 테넌트를 선택하여 접근할 수 있으며, 멤버십·MFA·서비스 이용 자격 검증을 충족한다.
- `User`, `Tenant`, `TenantMembership`, `Application`, `TenantApplication` 관계가 데이터 제약과 함께 검증된다.
- Papyrus는 Passport에서 발급한 전역 `tenant_id`를 재사용한다.
- 사용자 본인의 인증 성공만으로 타 테넌트 또는 미계약 SaaS 접근이 허용되지 않는다.
- 접근 자격 변경의 즉시 차단, 변경 대상별 버전·캐시 검증, Valkey 장애 시 DB 대체 검증 및 부분 실패의 안전한 재시도가 FR-APP-008-01~09에 따라 검증된다.
- 웹 브라우저는 BFF 세션 쿠키로 인증하고 Access/Refresh Token을 받지 않는다. BFF와 직접 API 클라이언트는 리소스 API를 Access Token으로 호출하며, 리소스 API는 세션 쿠키만으로 인증하지 않는다. 기존 로그인·철회·접근 자격 정책과 연결된 BFF 세션의 무효화가 검증된다.
- 외부 OIDC ID Token·외부 Access Token이 API 인증 수단으로 직접 수용되지 않으며, OIDC 기반 Passport 토큰에도 기존 로그인 유지·갱신·철회 정책과 테넌트 범위가 적용된다.
- DB 백업의 생성 시점부터 30일 기본 보존 정책과 복원 시 탈퇴·삭제 상태 재적용에 의한 재노출 방지가 검증된다(NFR-OPS-002-01).
- 백업 복원 후 기존 Local·OIDC 로그인 전체 종료, 복구 전 발급 Access Token의 Passport·연동 SaaS API 거부 및 Refresh Token 갱신 거부가 검증되고 탈퇴·차단·멤버십 해지·삭제 상태는 별도로 검증·재적용된다(NFR-OPS-002-02).
- 정보 보안 이벤트에 감사 추적이 남으며 로그에 비밀/토큰 원문이 없다. 감사로그의 기록 시점부터 365일 기본 보존 정책이 프로필 추가 보관 목표 24시간과 구분하여 검증된다(NFR-SEC-007-01).
- OpenAPI 계약과 Frontend 핵심 화면 E2E 테스트가 통과한다.
- D-01~D-03 등 토큰 신뢰 경계와 토큰 저장·전달 정책을 구현 전에 승인한다.

**요약:** Passport는 공통 Identity/Account/Authentication/Global Tenant의 Source of Truth이며, 외부 OIDC 설정과 인증 허용 범위는 테넌트별로 독립 관리한다. Local 인증은 기존대로 유지하고 로그인 후 소속 테넌트를 선택하여 접근할 수 있다. OIDC 인증에서는 대상 테넌트에 설정된 서비스만 이용하며, 다른 테넌트의 인증 결과를 재사용하여 접근할 수 없다. Papyrus 등 SaaS는 공통 사용자·테넌트·이용 자격을 참조하면서 도메인별 리소스와 세부 접근 정책을 소유한다. 가장 먼저 구체화할 설계 과제는 **Keycloak·Auth0 인증 검증 후 Passport 자체 Access Token을 발급하고, 서비스 간 SSO·API별 audience·외부 인증 출처 및 테넌트·MFA 컨텍스트·외부 인증 생명주기를 연결하는 계약**이다.
